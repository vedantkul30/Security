B. Mental models and core principles

1. What application security actually means

Application security is the practice of protecting an application's data, operations and infrastructure against unauthorized access, manipulation, disruption and disclosure.

Consider a portfolio-management application that stores:

  • Customer identities and account information.
  • Portfolio holdings and transaction records.
  • Trading research and investment decisions.
  • Administrative functions and audit records.

Different threats require different controls.

Asset Threat Required security property
Customer financial records Unauthorized disclosure Confidentiality
Transaction records Unauthorized modification Integrity
Portfolio API Excessive traffic or service failure Availability
Admin endpoint Unauthorized privilege use Access control
User credentials Theft or guessing Authentication security

A fundamental engineering principle is that security is a property of the entire system, not a single library, endpoint or encryption function.

Using HTTPS does not prevent an authenticated user from accessing another customer's portfolio. A strong password does not prevent SQL injection. A correctly implemented authorization check does not protect data that was accidentally exposed through logs.

Security requires multiple controls addressing different failure modes.

2. The CIA triad

Confidentiality

Information is accessible only to authorized parties.

Example: Customer A must not see Customer B's bank balance.

Typical controls: encryption in transit, access control, careful data handling and restricted logging.

Integrity

Data and operations must not be modified improperly, and unauthorized changes must be prevented or detected.

Example: A portfolio valuation record must not be silently altered by an unauthorized caller.

Typical controls: authorization, input validation, database constraints and cryptographic integrity mechanisms where appropriate.

Availability

Authorized users should be able to access the system and its services when needed.

Example: A market-data API should remain responsive during a traffic spike.

Typical controls: rate limiting, capacity management, redundancy, timeouts and recovery procedures.

The CIA triad is a classification tool, not a complete security strategy. Authentication, accountability, privacy and non-repudiation can also be important security requirements.

Trade-offs

Security properties can compete with operational objectives.

  • Stronger validation and cryptographic operations consume resources.
  • Aggressive rate limits can block legitimate users.
  • Broad data encryption can complicate search and recovery.
  • Strict availability controls can conflict with emergency access requirements.

Senior engineers identify the required security properties and design controls around the actual risk rather than maximizing one property in isolation.

3. Least privilege

Least privilege means granting a user, process or service only the permissions necessary to perform its intended work, for only as long as necessary.

Suppose a reporting service only needs to read portfolio balances. Giving it database administrator privileges is unnecessary and dangerous.

A better design grants it read access to the required data and nothing more.

Apply this principle to:

  • Application users and administrators.
  • Database accounts.
  • Backend services.
  • Cloud identities and deployment jobs.
  • Developer access to production systems.

Why it matters: if an account is compromised, its privileges determine how much damage the attacker can cause.

For example, a compromised read-only reporting service should not be able to modify transactions, create administrator accounts or delete customer records.

Least privilege also applies to data returned by an API. A customer may be allowed to view an account balance without receiving internal risk flags, database identifiers or other customers' details.

4. Defense in depth

Defense in depth means using multiple independent or complementary security controls so that the failure of one does not automatically compromise the entire system.

Consider a financial API:

  1. HTTPS protects data in transit.
  2. Authentication establishes the caller's identity.
  3. Authorization checks whether the caller may perform the requested operation.
  4. Input validation rejects malformed or unexpected values.
  5. Parameterized database queries prevent user input from being interpreted as SQL.
  6. Audit records help investigate sensitive operations.

These controls solve different problems. None replaces the others.

A practical example: HTTPS cannot stop an attacker who has legitimately authenticated using a stolen account from attempting unauthorized transactions. Authorization, transaction validation and monitoring remain necessary.

Important distinction: defense in depth does not mean adding as many controls as possible. Redundant controls that share the same failure mode may create complexity without meaningfully improving security.

5. Secure defaults

A secure default is the safest reasonable behavior when a developer or operator has not explicitly configured an option.

Examples:

  • Deny access unless a request is explicitly permitted.
  • Avoid exposing detailed internal exceptions to clients.
  • Do not publish administrative endpoints unnecessarily.
  • Require HTTPS for sensitive production traffic.
  • Avoid granting excessive privileges to database accounts.

Compare two hypothetical API designs:

// Illustrative pseudocode: insecure default
if (requestIsNotKnownToBeDangerous(request)) {
    allowRequest();
}
// Illustrative pseudocode: secure default
if (requestIsExplicitlyAuthorized(request)) {
    allowRequest();
} else {
    denyRequest();
}

The first design attempts to identify every dangerous request. The second permits only requests that meet an explicit policy.

The second approach is usually easier to reason about for access control because missing rules do not silently become permissions.

Secure defaults are not a substitute for configuration review. An application can still have an insecure explicitly configured exception.

6. Trust boundaries and attack surfaces

A trust boundary is a point where data, requests or execution cross between components with different levels of trust.

Examples include:

  • Browser to backend API.
  • Backend service to database.
  • Application to an external market-data provider.
  • Internet-facing API gateway to an internal service.
  • Administrator workstation to production infrastructure.

An attack surface is the set of exposed interfaces and behaviors through which an attacker may attempt to interact with a system.

It includes more than network ports. Public API endpoints, file uploads, administrative functionality, dependency interfaces, user-controlled input and operational tooling can all contribute.

Untrusted client

Browser, external caller or compromised client

Trust boundary

Validate request structure, enforce transport security, identify the caller and enforce access policy.

Backend application

Business rules and trusted internal processing

Database trust boundary

Use constrained database privileges, safe queries and appropriate transaction rules.

A reverse proxy may terminate TLS, but that does not mean the backend can trust arbitrary client-supplied identity headers. Trust must be established through a well-defined mechanism.

How to identify an attack surface

For every component, ask:

  • Who can reach it?
  • Which inputs can they control?
  • Which operations can those inputs trigger?
  • What privileges does the component possess?
  • What happens if its dependency is compromised?
  • What information does it reveal when something fails?

These questions form the basis of later threat modeling.

C. Authentication, authorization and identity

1. Authentication versus authorization

Authentication answers: Who is the caller?

Authorization answers: What is that caller allowed to do?

These are separate decisions.

Imagine a customer successfully signs in to a portfolio application. Authentication may establish that the caller is customer C102. Authorization must still determine whether that customer can read portfolio P900.

A valid identity does not imply unrestricted access.

Concept Meaning Example
Identity The entity's recognized identity Customer ID C102
Principal The identity represented during execution The current authenticated customer
Credentials Evidence presented to establish identity A password
Authentication Verification of identity Password verification succeeds
Authorization Decision about permitted actions Customer may read their own portfolio
Role A named grouping of responsibilities SUPPORT
Permission An allowed action on a resource portfolio:read

A role is not necessarily the same as a permission. A role can group multiple permissions, while a permission describes a specific capability.

2. The complete decision process

Decision Process Diagram
flowchart TD A["Incoming HTTP request"] --> B{"Valid request and transport?"} B -- No --> X["Reject or redirect according to policy"] B -- Yes --> C["Establish caller identity"] C --> D{"Identity verified?"} D -- No --> E["Authentication failure"] D -- Yes --> F["Evaluate action and resource policy"] F --> G{"Operation permitted?"} G -- No --> H["Authorization failure"] G -- Yes --> I["Execute business operation"] I --> J["Return permitted response"]

This is a conceptual flow, not a claim about the exact order of Spring Security filters or every HTTP deployment.

In a real system, transport security may be enforced by a reverse proxy. Request validation, authentication and authorization can occur at different layers, but the overall policy must remain correct.

3. Why role checks are not enough

Suppose an API exposes:

GET /api/portfolios/P900

The caller is authenticated and has the role CUSTOMER.

A weak policy checks only that the caller is a customer. That permits any customer to attempt access to any portfolio ID.

A correct policy also checks that the requested portfolio belongs to that customer, or that the caller has some explicitly authorized alternative access.

This illustrates a core principle: identity, role and resource ownership are distinct inputs to an authorization decision.

The syllabus covers this in depth in Topic 5. Here, remember that authentication alone never proves that access to a particular record is permitted.

D. HTTP and browser security

HTTP is the protocol through which browsers, mobile applications and backend services exchange requests and responses. Understanding its security properties is essential because most web-application security decisions occur around these messages.

1. Anatomy of an HTTP request

Consider this request to a hypothetical portfolio API:

GET /api/portfolios/P900 HTTP/1.1
Host: api.example.com
Accept: application/json
Authorization: Bearer <placeholder>

The request contains:

  • Method: GET, indicating the requested operation.
  • Path: /api/portfolios/P900, identifying the resource.
  • Headers: Metadata about the request and, potentially, information used for access control.
  • Body: Optional request data; this example has none.

A corresponding response might be:

HTTP/1.1 200 OK
Content-Type: application/json

{
  "portfolioId": "P900",
  "currency": "INR",
  "totalValue": 125000.00
}

The response contains a status code, headers and potentially a body.

The server must not assume that the request is trustworthy simply because it is syntactically valid. The caller can manipulate paths, query parameters, headers and body content.

HTTP request structure and client-server behavior are documented in MDN's HTTP overview.

2. HTTP versus HTTPS

HTTP describes application-level message exchange. HTTPS uses HTTP over a connection protected by TLS (Transport Layer Security).

TLS provides three important protections when correctly configured and the peer is properly authenticated:

  • Confidentiality: Network observers cannot ordinarily read the protected traffic.
  • Integrity: Unauthorized modifications to protected traffic are detected.
  • Server authentication: The client can verify that it is communicating with the server represented by a valid certificate, subject to correct certificate validation and trust configuration.

Plain HTTP does not provide these protections by itself.

Property HTTP without TLS HTTPS with correctly configured TLS
Protection against network eavesdropping No Yes
Detection of in-transit modification No cryptographic protection Yes
Server identity verification through a certificate No Yes
Protection against application-level authorization bugs No No
Protection against malicious code running in the browser No No

HTTPS is necessary for sensitive applications, but it is not a complete application-security solution.

For example, an attacker who obtains valid customer credentials may still sign in over HTTPS. Similarly, a backend that returns another customer's data to an authenticated user remains vulnerable even though every connection is encrypted.

3. What happens during TLS establishment?

At a high level, a TLS connection involves these steps:

TLS Handshake & Session Sequence
sequenceDiagram participant C as Client / Browser participant S as Server C->>S: Establish connection and propose TLS parameters S->>C: Select parameters and provide certificate C->>C: Validate certificate chain and hostname C->>S: Complete key establishment and handshake Note over C,S: Both sides establish traffic-protection keys C->>S: Encrypted HTTP request S->>C: Encrypted HTTP response

This is a conceptual sequence; exact handshake messages vary by TLS version and configuration.

The important distinction is that the certificate helps establish the server's identity, while the TLS handshake establishes the cryptographic context for protecting the connection.

A certificate does not prove that the application itself is safe. A malicious or compromised server can still have a valid certificate.

4. TLS certificates and trust

A TLS certificate binds a public key to an identity, such as a domain name, through a certificate issued or signed by a certificate authority (CA).

The client generally needs to verify:

  • The certificate chain leads to an accepted trust anchor.
  • The certificate is valid for the hostname being accessed.
  • The certificate is within its validity period.
  • Applicable certificate constraints and validation requirements are satisfied.

Production failure modes include expired certificates, missing intermediate certificates, incorrect hostnames and broken certificate renewal.

Senior-engineer lesson

Never disable certificate verification as a quick fix for a TLS error. Diagnose the trust-chain, hostname or configuration problem instead.

5. HTTP headers, cookies and bearer tokens

These mechanisms carry different types of information and must not be confused.

Request headers
Carry metadata and control information, such as Accept, Content-Type and Authorization. A header is client-controlled unless its authenticity is established through an appropriate trusted mechanism.

Cookies
Small pieces of data that a browser can store and send with matching requests according to cookie rules. Cookies can carry preferences or identifiers. A cookie carrying a session identifier is one common way to associate requests with server-side state; the detailed mechanism belongs to Topic 3.

Bearer tokens
Credentials whose possession allows the holder to exercise whatever authority the receiving service accepts for that token. A stolen bearer token can therefore be dangerous. The server must validate the credential and enforce the applicable access policy. Detailed token formats and implementation belong to Topic 6.

A useful HTTP distinction:

Authorization: Bearer <placeholder>

is an authorization header carrying a bearer credential. The word Bearer identifies the credential scheme; it does not by itself prove the credential is valid.

Never assume that a header is trustworthy just because it is named X-User-Id, X-Role or X-Internal-Request. If clients can supply it and the application trusts it without verification, it may become an impersonation vulnerability.

6. Origins and the same-origin policy

A browser origin consists of the scheme, host and port.

For example:

  • https://app.example.com
  • https://api.example.com
  • http://app.example.com
  • https://app.example.com:8443

These are different origins because at least one component differs.

The same-origin policy restricts how browser scripts can interact with resources belonging to another origin. It helps prevent a malicious website from freely reading information from another website that the user has opened or authenticated to. (Reference: MDN Same-Origin Policy)

However, three concepts must be kept separate:

  • Same-origin policy: A browser-enforced isolation mechanism.
  • CORS (Cross-Origin Resource Sharing): A mechanism through which servers indicate which cross-origin browser interactions are permitted.
  • Authorization: The application's decision about whether a particular caller may access a particular resource.

CORS is part of Topic 11, so we will not implement it here.

The critical lesson is that a browser security restriction is not a replacement for server-side access control. A script, command-line client or malicious application can make HTTP requests without following the same browser restrictions.

E. Cryptographic building blocks

Cryptography uses mathematical techniques to protect information, verify integrity and establish authenticity. It is important to choose a primitive based on the property the system needs rather than treating all cryptographic operations as interchangeable. (Reference: NIST Cryptography)

1. Encoding versus hashing versus encryption

This distinction is foundational.

Mechanism Primary purpose Reversible? Uses a secret key?
Encoding Represent data in a different format Yes, by design Usually no
Hashing Produce a fixed-size digest of input Not designed to be reversed Not necessarily
Encryption Protect information so authorized parties can recover it Yes, with the appropriate key Yes, in conventional secure encryption
Digital signature Provide evidence of origin and integrity Verification is possible; it is not encryption Uses a private signing key and a corresponding public key

Encoding

Base64 is an encoding scheme, not an encryption algorithm.

import java.nio.charset.StandardCharsets;
import java.util.Base64;

public class EncodingExample {
    public static void main(String[] args) {
        String original = "portfolio=P900";

        String encoded = Base64.getEncoder()
                .encodeToString(original.getBytes(StandardCharsets.UTF_8));

        String decoded = new String(
                Base64.getDecoder().decode(encoded),
                StandardCharsets.UTF_8
        );

        System.out.println(encoded);
        System.out.println(decoded);
    }
}

The encoded value can be decoded without possessing a secret.

Security implication

Never protect a password, API key or private financial data merely by Base64-encoding it.

Hashing

A cryptographic hash function maps input data to a fixed-length digest.

h = H(m) where m is the input and H is the hash function.

Common properties of a secure cryptographic hash include:

  • Preimage resistance: Given a digest, finding an input that produces it should be computationally infeasible.
  • Second-preimage resistance: Given an input, finding a different input with the same digest should be computationally infeasible.
  • Collision resistance: Finding any two distinct inputs with the same digest should be computationally infeasible.

Hashing is useful for integrity-related operations, digital-signature constructions and other cryptographic applications.

But hashing does not automatically authenticate the sender. An attacker who can modify both a message and an unkeyed hash can calculate a new hash for the modified message.

Another crucial distinction: general-purpose hashes such as SHA-256 are not, by themselves, suitable for password storage. Password hashing requires specialized, deliberately expensive algorithms. That implementation is covered in Topic 2.

Encryption

Encryption transforms plaintext into ciphertext using an algorithm and key.

c = Ek(m)

The authorized recipient uses the appropriate decryption operation to recover the message.

Encryption primarily protects confidentiality. Whether integrity and authenticity are also protected depends on the scheme used.

For example, modern authenticated encryption provides both confidentiality and integrity under its intended usage assumptions.

2. Symmetric versus asymmetric cryptography

Symmetric cryptography

The communicating parties share a secret key. One key is used for encryption and the corresponding decryption operation.

Strengths: Efficient and well suited to protecting large amounts of data.

Challenge: The parties must establish and protect the shared secret.

Example: AES-based authenticated encryption.

Asymmetric cryptography

Uses a mathematically related public/private key pair. The public key can be distributed; the private key must be protected.

Strengths: Supports operations such as digital signatures and key establishment without requiring every party to share the same secret beforehand.

Challenge: Requires correct key management and authenticated public-key associations.

Examples: RSA and elliptic-curve cryptography, with different algorithms serving different purposes.

Do not assume that every asymmetric algorithm can be used interchangeably for encryption, key agreement and signatures. Their supported operations and security requirements differ.

3. Digital signatures

A digital signature allows a verifier to check whether a message was signed using the private key corresponding to a particular public key, and whether the signed content has changed.

Conceptually:

s = Signsk(m)
Verifypk(m, s) → {valid, invalid}

Here, sk is the private signing key and pk is the corresponding public key.

Suppose a market-data provider signs a data package. A consumer can verify the signature using the provider's trusted public key. This helps detect tampering and verify that the package was signed by the holder of the corresponding private key.

A digital signature does not encrypt the message. Anyone with access to the signed message can generally read its contents.

Nor does a valid signature alone establish that the signer's claims are truthful or that the signer is authorized to perform every requested action.

See the NIST Digital Signatures overview for the underlying security properties.

4. Public and private key management

A cryptographic design is only as strong as its key handling.

Consider the following risks:

  • A private key committed to a public Git repository.
  • A shared secret copied into multiple unrelated services.
  • A key accessible to every application developer.
  • An expired or compromised certificate that is not replaced.
  • A key that is backed up insecurely or cannot be recovered when needed.

Good engineering separates key use, access control, rotation and storage from ordinary application configuration wherever appropriate.

Do not hardcode production secrets into Java source code. Use the deployment environment's approved secret-management mechanisms and restrict who can access them.

5. Randomness

Security-sensitive random values must be unpredictable to an attacker.

Examples include cryptographic keys and secret tokens. Ordinary random-number generators intended for simulations or games may produce predictable values and are not appropriate for such purposes.

Java provides SecureRandom for cryptographically strong random-number generation.

import java.security.SecureRandom;
import java.util.HexFormat;

public class RandomValueExample {

    private static final SecureRandom RANDOM = new SecureRandom();

    public static void main(String[] args) {
        byte[] randomBytes = new byte[32];
        RANDOM.nextBytes(randomBytes);

        String value = HexFormat.of().formatHex(randomBytes);
        System.out.println(value);
    }
}

This generates 32 random bytes, represented as a 64-character hexadecimal string.

The output is illustrative and should not be treated as a real credential. In production, use the value for an explicitly defined security purpose, protect it as necessary, and avoid printing secrets to logs.

Randomness is not a substitute for access control. A hard-to-guess identifier should not be treated as proof that its holder is authorized to access a resource.

F. Common attacks and how they work

The goal of this section is to understand the attacker's objective, the underlying weakness, the impact and the appropriate defensive principle.

1. Brute force and credential stuffing

These attacks both target account access, but they work differently.

Brute-force attack
The attacker repeatedly guesses possible passwords for an account.
Example: Trying many candidate passwords against a customer login endpoint.
Defenses: Login throttling, rate limiting, monitoring, strong password practices and MFA where appropriate.

Credential stuffing
The attacker uses username/password combinations exposed by earlier breaches to attempt access to other services.
Example: Trying leaked credentials from an unrelated website against a banking application.
Defenses: MFA, rate limiting, detection of suspicious login patterns, compromised-password screening and safe account-recovery procedures.

Why credential stuffing can succeed: users sometimes reuse passwords across services. A strong password on one website offers little protection if the same password has already been compromised elsewhere.

Why rate limiting alone is insufficient: attackers can distribute attempts across IP addresses, accounts and infrastructure. Defensive systems need to consider the wider pattern without unnecessarily locking out legitimate users.

Account throttling and password-storage implementation receive deeper treatment in Topic 2.

2. Phishing

Phishing attempts to trick a person into disclosing credentials or approving an action they did not intend.

Example: A customer receives a convincing message linking to a fraudulent website that imitates a legitimate investment platform.

The attacker may capture the customer's password or other sensitive information.

Defensive measures include:

  • Verifying website domains before entering credentials.
  • Using phishing-resistant authentication where appropriate.
  • Avoiding login links from untrusted messages.
  • Educating users about fraudulent requests.
  • Providing a safe and clearly identifiable account-recovery process.

HTTPS does not prove that a website is legitimate. A fraudulent domain can also obtain a valid TLS certificate for its own domain.

3. Replay attacks

A replay attack occurs when an attacker captures a previously valid message or request and sends it again to trigger an unintended effect.

Imagine a payment API accepting this request:

POST /api/transfers
Content-Type: application/json

{
  "fromAccount": "A100",
  "toAccount": "A200",
  "amount": 5000
}

If the API processes every identical submission as a new transfer, a repeated request could cause multiple transfers.

The underlying problem is not necessarily that the request was modified. It is that the system did not correctly handle repeated execution.

Defensive approaches depend on the operation:

  • Use idempotent API semantics where appropriate.
  • Apply an idempotency mechanism to operations that must not execute twice.
  • Use unique transaction identifiers and database constraints where suitable.
  • Validate freshness or request context when the protocol requires it.
  • Track the state of sensitive operations.

Important: Encryption alone does not universally prevent replay. A previously valid encrypted message may still be replayable unless the protocol or application handles freshness and duplicate execution.

Detailed token-replay and authentication-lifecycle controls belong to their later syllabus topics.

4. SQL injection

SQL injection occurs when untrusted input changes the structure or meaning of a database query.

Consider an intentionally unsafe Java example:

String sql = "SELECT * FROM users WHERE email = '"
        + email
        + "'";

The code treats email as part of the SQL program itself. If the value contains SQL syntax, the resulting query can behave differently from what the developer intended.

The underlying mistake is mixing data with executable query structure.

The correct approach is to use parameterized queries, which keep the query structure separate from user-supplied values.

String sql = "SELECT id, email FROM users WHERE email = ?";

try (var connection = dataSource.getConnection();
     var statement = connection.prepareStatement(sql)) {

    statement.setString(1, email);

    try (var results = statement.executeQuery()) {
        while (results.next()) {
            System.out.println(results.getString("email"));
        }
    }
}

This example illustrates JDBC parameter binding; production code should also apply appropriate error handling and data-access-layer design.

Why it is safer: the database driver binds the email as a value rather than inserting it into the SQL syntax.

Additional defenses include least-privilege database accounts and validation of expected input formats. Validation alone is not a replacement for parameterized queries.

The same general principle applies to other interpreters: do not allow untrusted data to become executable instructions.

5. Cross-site scripting (XSS)

XSS occurs when an application causes attacker-controlled content to execute as script in a victim's browser.

Suppose a portfolio application displays a user's profile description. If it inserts untrusted content into an HTML document without appropriate contextual output encoding or sanitization, an attacker may inject executable markup or script.

Potential impact includes:

  • Reading information available to the affected page.
  • Performing actions as the victim through the browser.
  • Modifying page content to mislead users.
  • Attempting to steal accessible credentials or session material.

Defenses include context-appropriate output encoding, safe rendering APIs, sanitization when HTML must be accepted, and restrictive browser security policies.

HTTPS does not prevent XSS because the vulnerability exists in how the application handles content, not necessarily in how the content travels over the network.

Detailed output handling and browser protections are covered in Topic 11.

6. Cross-site request forgery (CSRF)

CSRF occurs when a malicious site causes a victim's browser to send a request to another site where the victim has an authenticated context, potentially triggering an unwanted action.

For example:

  1. A customer is signed in to a financial application.
  2. The browser retains an authentication cookie.
  3. The customer visits a malicious website.
  4. That website attempts to trigger a sensitive request to the financial application.
  5. If the application accepts the request without adequate CSRF defenses, the operation may succeed.

The key issue is that a browser may automatically attach certain credentials, such as applicable cookies, to requests. The server cannot assume that a request originated from an intentional user action simply because the browser supplied a credential.

Defenses depend on the authentication design and browser behavior. They can include CSRF tokens, appropriate cookie attributes, origin-related checks and restrictions on sensitive operations.

Scope boundary: We will study CSRF protection in more detail alongside server-side sessions in Topic 3 and comprehensive web-security controls in Topic 11.

7. Broken access control and information leakage

Broken access control occurs when the application fails to enforce the intended restrictions on an action or resource.

Example:

GET /api/accounts/501

The server verifies that the caller is authenticated but fails to check whether the caller may access account 501.

An attacker can change the identifier and attempt to access another account.

This type of flaw is commonly associated with insecure direct object references (IDOR), and API security discussions also use the term broken object-level authorization (BOLA).

Defenses include:

  • Checking authorization on every protected operation.
  • Enforcing ownership or other resource-level policies.
  • Denying access by default.
  • Returning only data the caller is allowed to see.
  • Testing requests across multiple users and privilege levels.

OWASP's Authorization Cheat Sheet recommends least privilege, explicit access-control design and checks on the particular resources being accessed.

Information leakage is broader than access-control failure. It includes accidentally exposing:

  • Stack traces and internal exception messages.
  • Database queries and internal hostnames.
  • Passwords, credentials or tokens in logs.
  • Private user details in API responses.
  • Sensitive data through debugging endpoints.

A secure error response should give the caller enough information to understand the outcome without disclosing unnecessary internal details.

G. End-to-end engineering scenario: A protected portfolio endpoint

Let's combine the fundamentals into a realistic design exercise.

Requirements

Build a portfolio API that lets customers read their own portfolio while preventing unauthorized access to other customers' financial information.

Assume the application has a Java backend, an HTTP API and a relational database.

Threat model

The attacker may:

  • Send requests without authentication.
  • Modify request paths, parameters or headers.
  • Guess another customer's portfolio identifier.
  • Send malformed or unexpected input.
  • Repeat requests.
  • Attempt to infer internal details from error responses.

The design should protect customer confidentiality, preserve data integrity and keep the service available to legitimate callers.

Request flow

End-to-End Decision Flow

Design decisions

1. Establish identity before relying on identity claims.
The application must obtain the caller's identity through a defined authentication mechanism. It must not blindly trust a customer ID supplied in a request header or body.

2. Check access to the specific resource.
Knowing that the caller is a customer is insufficient. The application must verify access to the requested portfolio.

3. Retrieve only necessary data.
Use a data-access operation that retrieves the relevant record and, where appropriate, incorporates the ownership constraint into the query.

4. Minimize error information.
An unauthenticated request, a forbidden operation and a missing resource may warrant different responses depending on the API's policy. Do not expose stack traces or database details to explain a failure.

5. Limit operational privileges.
The API's database identity should have only the privileges needed by the application. A read-only portfolio endpoint should not require broad administrative database access.

Example outcome matrix

Request condition Expected outcome
No valid authentication Reject the protected request
Authenticated caller owns the portfolio Return permitted portfolio data
Authenticated caller does not own the portfolio Deny access or use a documented safe response
Portfolio does not exist Return the documented missing-resource response
Invalid or malformed input Reject the request
Database unavailable Fail safely and report an appropriate service error

The exact HTTP status for a missing resource versus an inaccessible resource depends on the API's documented policy. Consistency and avoiding sensitive existence leaks are more important than blindly using one status code in every situation.

H. Architecture and system-design considerations

Security requirements affect the design of an application before any framework code is written.

1. Separate responsibilities

A maintainable backend commonly separates:

  • Transport layer: Accepts HTTP requests and constructs responses.
  • Identity and access-control layer: Establishes identity and evaluates access policy.
  • Business layer: Enforces business invariants, such as whether a transaction is valid.
  • Data-access layer: Retrieves and modifies records using controlled database operations.
  • Operational layer: Handles deployment configuration, logs, monitoring and recovery.

These are logical responsibilities; they do not necessarily require separate microservices.

A single well-structured Spring Boot application may be simpler and safer than several services with poorly defined trust boundaries.

2. Security controls at multiple layers

Consider a sensitive transaction endpoint.

Layer Responsibility
Network and transport Protect communication and restrict unnecessary exposure
HTTP/API Validate request structure and apply endpoint-level policy
Identity and authorization Verify the caller and their permission for the requested operation
Business logic Enforce transaction limits, state transitions and business invariants
Database Maintain constraints, transaction consistency and appropriately restricted privileges
Operations Detect suspicious activity and support investigation and recovery

A transaction can pass authentication and authorization checks but still be invalid under business rules. For example, an otherwise authorized customer may attempt to transfer more than the available balance.

Authentication, authorization and business validation are related, but they are not interchangeable.

3. Single-instance versus distributed deployment

A single-instance application may keep some operational state in process memory. A horizontally scaled application has multiple instances that may handle requests independently.

This changes the design questions:

  • Which component is authoritative for identity and permissions?
  • Can a security decision rely on stale information?
  • Are security-sensitive records shared consistently?
  • What happens if one instance is compromised?
  • Can logs and audit records be correlated across instances?
  • Do services have more privileges than their responsibilities require?

For this topic, the key lesson is to define trust and responsibility boundaries. Distributed authentication state, session storage and token architecture will be covered in later topics.

4. Fail safely

Suppose the application cannot establish whether a caller is authorized because a required dependency is unavailable.

For a sensitive read or write, the system should not silently allow access merely because the check failed.

At the same time, failure handling should be deliberate: return an appropriate error, log the event safely, and avoid retry loops that worsen the outage.

The correct behavior depends on the operation and security requirement, but a failed security check must not accidentally become permission to proceed.

I. Security review and attack scenarios

A useful security review does not simply ask, "Is the endpoint secure?" It identifies assets, attacker capabilities, exploitation conditions, impact and evidence that defenses work.

Scenario 1: A customer accesses another customer's portfolio

Asset: Financial data · Threat: Unauthorized disclosure
  • Attacker capability: Can sign in using their own account and change request parameters.
  • Precondition: The endpoint checks authentication but not resource ownership.
  • Exploitation path: The caller changes the portfolio ID in the URL.
  • Impact: Another customer's data is disclosed.
  • Mitigation: Enforce resource-specific authorization on every request.
  • Verification: Create two test customers and verify that neither can access the other's portfolio.
  • Residual risk: Other endpoints may still expose the same records if they do not enforce equivalent policies.

Scenario 2: A malicious request changes a database query

Asset: Database records · Threat: Unauthorized disclosure or modification
  • Attacker capability: Controls an input incorporated into a SQL statement.
  • Precondition: Application code constructs query syntax through unsafe string concatenation.
  • Exploitation path: Crafted input changes the intended query structure.
  • Impact: Depending on database privileges and query behavior, data could be disclosed, modified or deleted.
  • Mitigation: Use parameterized queries and restrict database privileges.
  • Verification: Test adversarial inputs and verify that they are treated as data, not executable query syntax.
  • Residual risk: Other database operations may contain unsafe query construction.

Scenario 3: A valid request is repeated

Asset: Transaction integrity · Threat: Duplicate operation
  • Attacker capability: Can resend a previously valid request.
  • Precondition: The operation processes repeated requests as independent actions.
  • Exploitation path: A transfer or other state-changing operation is submitted more than once.
  • Impact: Duplicate transactions or other unintended state changes.
  • Mitigation: Define correct operation semantics and use suitable deduplication or idempotency controls.
  • Verification: Submit the same operation repeatedly and verify the documented outcome.
  • Residual risk: Deduplication may fail if state is not stored or checked consistently.

Scenario 4: A developer trusts a client-supplied identity header

Asset: User identity and privileges · Threat: Impersonation
  • Attacker capability: Can modify HTTP request headers.
  • Precondition: The application treats an unverified header as authoritative identity information.
  • Exploitation path: The caller supplies a different user's ID or an elevated role.
  • Impact: Impersonation or privilege escalation.
  • Mitigation: Establish identity through a trusted authentication mechanism and explicitly define which infrastructure may set trusted headers.
  • Verification: Send forged identity and role headers directly to the API and confirm that they do not grant additional access.
  • Residual risk: Incorrect proxy trust configuration or other identity-handling paths may remain vulnerable.

These examples demonstrate why threat modeling must cover the entire request path, not just the happy path.

J. Engineering trade-offs and design decisions

A senior engineer chooses security controls based on the threat model, operational constraints and consequences of failure.

Decision Option A Option B What should drive the choice?
API access policy Allow unless explicitly blocked Deny unless explicitly permitted Prefer explicit permission for protected resources
Database access Broad database account Least-privilege account Required operations and potential impact of compromise
Query construction String concatenation Parameterized queries Parameterization for user-supplied query values
Error responses Detailed internal errors to clients Safe external errors with internal diagnostics Confidentiality and operational usefulness
Network transport Plain HTTP Properly configured HTTPS Sensitive web/API traffic requires transport protection
Security architecture One large application with clear boundaries Multiple services with network boundaries Actual scaling, ownership, isolation and operational needs
Access verification Check only the user's role Check the role and resource-specific policy Whether the operation depends on ownership or other attributes

Some choices have strong default recommendations. For example, parameterized SQL queries are preferable to string-concatenated queries containing untrusted input.

Other choices require more context. Splitting an application into more services can improve isolation in some cases, but it also creates more interfaces, credentials and failure modes to secure.

The cost of a security control

For every control, ask:

  1. Which threat does it reduce?
  2. What assumptions does it depend on?
  3. What happens when it fails?
  4. What performance and maintenance costs does it introduce?
  5. How will its effectiveness be verified?
  6. Does another layer already provide a relevant protection, or is there still a gap?

A control without a clear threat or verification strategy may create complexity without delivering meaningful security.

K. Common implementation mistakes and debugging

Mistake 1: Assuming HTTPS makes the application secure

Why it happens: Developers conflate transport security with application security.

Runtime symptom: Requests are encrypted, but a caller can still retrieve records belonging to another customer.

Diagnosis: Test resource-level access using multiple identities. Inspect the authorization decision, not just the TLS connection.

Correction: Implement the correct access policy and verify it independently of transport protection.

Mistake 2: Treating encoding as encryption

Why it happens: Encoded values look different from their original representation.

Runtime symptom: A supposedly protected value can be decoded without any secret.

Diagnosis: Determine whether the operation is a reversible representation change or a cryptographic transformation.

Correction: Choose the primitive based on the security property required.

Mistake 3: Trusting client-supplied roles or IDs

Why it happens: A request header or body field appears to provide convenient identity information.

Runtime symptom: Changing a request field changes the effective identity or privilege of the caller.

Diagnosis: Compare requests containing legitimate and forged identity-related values. Trace where the server obtains the authoritative identity.

Correction: Use a trusted identity mechanism and enforce access policies on the server.

Mistake 4: Returning every exception to the client

Why it happens: Detailed errors make debugging easier during development.

Runtime symptom: API responses reveal internal package names, SQL details, hostnames or stack traces.

Diagnosis: Trigger representative failures and inspect responses, logs and monitoring output.

Correction: Return controlled external errors while preserving appropriate internal diagnostics. Avoid logging secrets or sensitive data.

Mistake 5: Assuming browser restrictions protect every API client

Why it happens: A developer relies on the same-origin policy as if it were server-side access control.

Runtime symptom: A request from a command-line client bypasses assumptions based on browser behavior.

Diagnosis: Exercise the endpoint directly without relying on the browser's protections.

Correction: Enforce authentication, authorization and input validation at the appropriate server-side boundaries.

Mistake 6: Using ordinary randomness for security-sensitive values

Why it happens: A conventional pseudo-random generator appears sufficient for testing or ordinary application logic.

Runtime symptom: Sensitive values may be predictable if the generation method is unsuitable.

Diagnosis: Inspect how security-sensitive values are generated and whether the API is intended for cryptographic use.

Correction: Use an appropriate cryptographically secure generator, such as Java's SecureRandom.

L. Testing and verification

Security testing must prove not only that legitimate operations work, but also that unauthorized operations fail.

1. A practical test matrix

For the portfolio API, design tests around these dimensions:

Test dimension Example Expected property
Identity No authenticated caller Protected data is not returned
Ownership Customer A requests Customer B's portfolio Access is denied
Input Malformed portfolio identifier Request is rejected safely
Injection SQL-like input in a search field Input is not interpreted as query syntax
Information exposure Internal dependency failure No sensitive internal details reach the client
Replay Same transfer request is submitted twice Behavior matches the operation's defined semantics
Identity-header spoofing Caller supplies a forged role header No unauthorized privilege is granted
Availability Excessive repeated requests Appropriate resource protection is applied

Some tests are integration tests; others require HTTP-level tests or deployment-level verification. No single test proves the entire application is secure.

2. A simple JUnit example

The following example tests a pure authorization policy. It is intentionally framework-independent because Topic 4 will cover Spring Security's implementation details.

import org.junit.jupiter.api.Test;

import static org.junit.jupiter.api.Assertions.*;

class PortfolioAccessPolicyTest {

    record User(String id, String role) {}

    static boolean canReadPortfolio(
            User user,
            String portfolioOwnerId) {

        return user != null
                && portfolioOwnerId != null
                && (
                    "ADMIN".equals(user.role())
                    || user.id().equals(portfolioOwnerId)
                );
    }

    @Test
    void ownerCanReadOwnPortfolio() {
        User alice = new User("alice", "CUSTOMER");

        assertTrue(canReadPortfolio(alice, "alice"));
    }

    @Test
    void customerCannotReadAnotherUsersPortfolio() {
        User alice = new User("alice", "CUSTOMER");

        assertFalse(canReadPortfolio(alice, "bob"));
    }

    @Test
    void missingUserIsDenied() {
        assertFalse(canReadPortfolio(null, "alice"));
    }

    @Test
    void missingOwnerIsDenied() {
        User alice = new User("alice", "CUSTOMER");

        assertFalse(canReadPortfolio(alice, null));
    }
}

This is illustrative code that can be used as a starting point for a Java 17+ project with JUnit 5.

It demonstrates a policy rule, not a complete production authorization system. In a real application, the trusted user identity must be established correctly, roles must come from a trusted source, and resource ownership must reflect actual database state.

The ADMIN exception is also a business-policy assumption, not a universal rule. Some systems restrict administrators' access to financial records as well.

3. What the test does and does not prove

It proves that the policy returns the expected result for the supplied cases.

It does not prove that:

  • The application always invokes the policy.
  • The user identity is authentic.
  • The owner ID was retrieved correctly.
  • Other API endpoints enforce equivalent restrictions.
  • Database queries are safe.
  • The policy is applied consistently under concurrency or failure.

This distinction is essential in senior-level testing: a passing unit test proves behavior within its tested boundary, not the security of the entire system.

4. Testing strategy

Use a layered approach:

  1. Unit tests: Verify security decisions and business rules.
  2. Integration tests: Verify that application components work together correctly.
  3. HTTP-level tests: Verify observable behavior for successful and rejected requests.
  4. Adversarial tests: Attempt unauthorized access, malformed input and forged identity information.
  5. Deployment verification: Confirm that actual network, certificate and runtime configuration matches the intended security design.

A negative test is not an optional extra. It is evidence that the intended restriction is enforced.

2. Logging and monitoring

Security logs should help engineers answer questions such as:

  • Were there repeated failed authentication attempts?
  • Was a protected operation denied?
  • Did a user attempt to access a resource outside their permitted scope?
  • Did a security-related configuration change occur?
  • Did an unusual pattern emerge across several endpoints?

Log relevant metadata, such as timestamps, request or correlation IDs, operation types and outcomes, according to your logging policy.

Avoid logging passwords, secret keys, bearer credentials or unnecessary sensitive financial information.

Logs themselves require access controls, retention policies and integrity protections appropriate to their purpose.

3. Configuration and dependency maintenance

A secure local configuration does not guarantee a secure production deployment.

Verify the actual environment, including:

  • TLS termination and internal communication assumptions.
  • Database permissions.
  • Access to secret material.
  • Debug and administrative interfaces.
  • Error-handling behavior.
  • Dependency versions and security advisories.

Do not assume that a security feature is enabled merely because a framework supports it.

N. How a Senior Engineer Thinks About This

An experienced engineer does not begin with the question, "Which security library should I install?"

They begin by identifying what needs protection, who might attack it, what the attacker can control and what failure would cost.

1. The security decision framework

  1. Identify assets. What data, operations, identities and infrastructure would cause harm if compromised?
  2. Define trust boundaries. Which clients, services and dependencies are trusted, and why?
  3. Enumerate attacker capabilities. Can the attacker modify requests, steal credentials, repeat operations or exploit a dependency?
  4. Define security properties. Is the primary requirement confidentiality, integrity, availability, or some combination?
  5. Choose controls. Select controls that directly address the identified threats.
  6. Plan failure behavior. Decide what happens when identity verification, authorization, storage or a dependency fails.
  7. Establish evidence. Define tests, logs, configuration checks and operational signals that demonstrate the design works.

2. Questions to ask during a design review

For a financial API, ask:

  • Can a caller influence which identity the backend associates with the request?
  • Can an authenticated user access a record they do not own?
  • What happens if an attacker sends malformed or repeated requests?
  • Can the system leak internal information when a dependency fails?
  • Does any service have privileges beyond what it needs?
  • What happens if a credential or private key is compromised?
  • Which assumptions depend on the browser, proxy, network or deployment environment?
  • What test demonstrates that each critical security restriction actually works?

A good design review ends with verifiable requirements, not just statements that the design is secure.

3. Five principles worth internalizing

  • Trust must be established, not assumed.
  • Authentication does not imply authorization.
  • Encryption does not fix broken application logic.
  • Every externally controlled input deserves scrutiny at its trust boundary.
  • A security control is only useful if it is correctly configured, maintained and verified.

Scenario Review Prompt

You are reviewing an API that:

  • Uses HTTPS.
  • Requires users to sign in.
  • Returns portfolio data based on a request-supplied portfolio ID.

Assignment

Build a security-aware Java API

Create the design and core policy for a portfolio-read endpoint that protects customer data. Focus on the security fundamentals learned in this topic rather than implementing a complete authentication framework.

Requirements

  • Use Java 17+.
  • Define a customer identity and a portfolio resource.
  • Define an explicit policy for who may read a portfolio.
  • Treat request-supplied IDs and headers as untrusted input.
  • Return only the fields permitted by the API contract.
  • Handle missing resources and dependency failures safely.
  • Define a least-privilege database access requirement.

Required components

  • PortfolioController
  • PortfolioService
  • PortfolioRepository
  • PortfolioAccessPolicy
  • A consistent error-response model

Acceptance criteria

  • A permitted customer can read their own portfolio.
  • A customer cannot read another customer's portfolio.
  • Missing identity information does not grant access.
  • Forged identity headers do not elevate privileges.
  • Unexpected input is handled safely.
  • Internal exceptions and sensitive values are not exposed to clients.
  • Tests cover successful and denied requests.

Suggested tests

  • Owner access.
  • Cross-customer access.
  • Missing identity.
  • Missing portfolio.
  • Malformed identifiers.
  • Database failure.
  • Forged role or identity headers.

Optional extension

Write a short threat model identifying the assets, trust boundaries, attacker capabilities, attack scenarios and mitigations.

Do not begin by adding every possible security feature. First write the policy in plain English, then implement the smallest design that satisfies it and test its negative cases.
