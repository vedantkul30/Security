Topic 2 — Password Hashing and Secure Account Authentication

Backend Engineering & Application Security · Senior Engineer Study Notes · Java 17+ / Spring Boot

This topic moves from the security fundamentals in Topic 1 to implementing secure password-based authentication in a real backend application.

The central engineering problem is straightforward to state but easy to get wrong: how do you verify that a user knows their password without storing the password itself, and how do you build an account lifecycle that remains secure under attacks and failures?

We will cover password hashing, BCrypt, Argon2id, PBKDF2, scrypt, registration, login, password recovery, rate limiting, and secure account management. The implementation will use Java and Spring Boot with a relational database.

The syllabus order remains unchanged. Cookies and server-side sessions belong to Topic 3; Spring Security architecture belongs to Topic 4; JWT and other token-based authentication mechanisms belong to later topics. We will not implement those mechanisms here.

B. Mental model: what secure password authentication actually does

1. The fundamental problem

Suppose an application has one million customers. Each customer chooses a password, and the application must later determine whether a login attempt supplies the correct password.

A naive implementation stores this:

User Stored password
Alice MySecretPassword!
Bob AnotherSecret123

This design creates a catastrophic failure mode: anyone who obtains a database dump immediately obtains the users' passwords.

Those passwords may also unlock users' email accounts, other websites or financial applications if they have reused them.

The application should instead store a password hash produced by a password-hashing algorithm.

User Stored password representation
Alice Encoded password-hash string
Bob Encoded password-hash string

During registration, the application hashes the supplied password and stores the result. During login, it checks the supplied password against the stored hash using the appropriate password-verification algorithm.

The application does not need to recover the original password.

2. Registration versus login

Registration

User supplies password → Validate password and account data → Password-hashing algorithm generates encoded hash → Store encoded hash in database

Login

User supplies password → Retrieve account's stored hash → Password encoder verifies supplied password against stored hash → Match: continue login · No match: reject

The same operation should not be used for both purposes.

  • Registration creates a new encoded password hash.
  • Login verifies a candidate password against an existing encoded hash.

With BCrypt, hashing the same password twice normally produces different encoded results because each hash uses its own random salt. Consequently, login must use a verification operation rather than comparing two newly generated hash strings.

3. What password hashing does not solve

Password hashing protects stored passwords against straightforward recovery if the database is exposed. It does not automatically prevent:

  • Phishing or users voluntarily disclosing passwords.
  • Password reuse across websites.
  • Online guessing against the login endpoint.
  • A compromised application reading a password before hashing.
  • Malicious code or administrators with access to sensitive runtime data.
  • Account takeover through a poorly designed password-reset process.

This distinction matters because a secure account system requires several complementary controls, not just a strong hashing algorithm.

C. Password storage fundamentals

1. Why plaintext storage is unacceptable

If an attacker obtains plaintext passwords, no additional cracking step is necessary.

Even if the application has strict network security and correct access controls, a database backup, SQL injection vulnerability, compromised database credential or insider threat can expose the data.

A password-hashing design reduces the consequences of such an incident. It cannot make a compromised database harmless, but it can make password recovery substantially more difficult.

Plaintext storage also creates operational risks:

  • Database backups become extremely sensitive.
  • Developers may accidentally copy credentials into logs or debugging output.
  • Insider access can expose every customer's secret.
  • Password reuse can turn a single breach into compromise of other services.

Fundamental Rule

Never store, log or return a user's plaintext password.

2. Hashing versus encryption

Property Password hashing Encryption
Primary purpose Verify a candidate password without recovering the original Recover protected information when authorized
Reversibility Designed to resist reversing the transformation Intentionally reversible with the appropriate key
Key management Password hashes typically use salts and algorithm parameters rather than an application decryption key Requires secure encryption-key management
Password verification Supported through a password-specific verification operation Requires decryption to recover the stored password
Appropriate default for ordinary password storage Yes No

Why not encrypt passwords and decrypt them during login? Because the application would need access to a decryption key that could expose every stored password if compromised.

Password hashing avoids creating that requirement.

3. Salt: why identical passwords should produce different hashes

A salt is a random value generated for an individual password hash.

Conceptually:

h = Hpassword(p, s, c)

where:

  • p is the password.
  • s is the salt.
  • c represents algorithm configuration, such as a work factor.

This is a conceptual expression; actual algorithms have their own precise constructions.

Suppose Alice and Bob both choose the same password.

Without per-password salts, a password-hashing system may produce the same stored digest for both accounts. An attacker can identify identical passwords and reuse precomputed results.

With independent salts, the same password normally produces different encoded hash values.

Salts help by:

  • Preventing direct comparison of identical passwords from their stored hashes.
  • Defeating the straightforward reuse of precomputed password-hash tables across accounts.
  • Making an attacker perform separate candidate computations for each salt.

A salt is generally not a secret. It is stored alongside the encoded password hash.

Important distinction

A salt does not make a weak password strong, and it does not eliminate the need for a deliberately expensive password-hashing algorithm.

4. Work factor and computational cost

A work factor controls the resources required to calculate a password hash.

The purpose is to make large-scale password guessing expensive.

If one candidate password takes t seconds to verify, then testing N candidates requires approximately:

T ≈ N × t

This is a simplified model that ignores parallelism, hardware differences and algorithm-specific costs. It nevertheless captures the basic trade-off.

For example, if an attacker must test one million candidates and each verification takes 100 milliseconds on the attacker's hardware, the total sequential computation would be about 100,000 seconds, or 27.8 hours.

Real attackers may use parallel hardware, and the actual time depends on the algorithm, hardware and candidate strategy. The example illustrates the relationship, not a benchmark for any particular algorithm.

Increasing work factor generally makes each password verification more expensive for both attackers and your application.

That creates an engineering trade-off:

  • Too little cost makes offline guessing cheaper.
  • Too much cost can degrade login latency and exhaust application resources.

The correct setting must be benchmarked on the target production environment.

5. Offline versus online password attacks

These are different attack environments.

Offline attack
The attacker has obtained stored password hashes and guesses passwords locally. The attacker does not need to contact your login API for each guess.
Main defense: Use a suitable password-hashing algorithm, appropriate cost parameters, strong user passwords and secure database practices.

Online attack
The attacker repeatedly submits guesses to the login endpoint. Each attempt consumes application and infrastructure resources.
Main defenses: Rate limiting, throttling, suspicious-activity detection, secure recovery controls and additional authentication protections where appropriate.

Increasing the password-hashing cost makes offline cracking more expensive, but also makes online login attempts more expensive for your own server.

That is why a production design needs both suitable password hashing and controls around login traffic.

D. Password-hashing algorithms

Not all hash functions are designed for the same job.

1. Why SHA-256 alone is unsuitable

SHA-256 is a cryptographic hash function designed to be efficient. That is useful for many applications, but undesirable for password storage.

If an attacker obtains a database of SHA-256 password hashes, the attacker can test candidate passwords at high speed, particularly with specialized hardware.

Adding a salt helps prevent precomputed-table attacks and cross-account hash comparisons, but does not make SHA-256 sufficiently expensive for password storage.

The correct approach is to use a password-hashing algorithm with configurable computational cost, and, where appropriate, memory cost. OWASP recommends Argon2id for new password-storage systems, with alternatives for compatibility and compliance requirements. (OWASP Cheat Sheet Series)

2. Algorithm comparison

Argon2id

Preferred for new systems · Memory-hard password hashing

Argon2id combines design properties intended to resist different classes of password-cracking attacks, including attacks using specialized parallel hardware.

Configurable parameters:

  • Memory cost: amount of memory used.
  • Time cost: number of passes.
  • Parallelism: degree of parallel execution.

Trade-off: Memory use can constrain how many concurrent verifications the application can perform. Production configuration must consider both offline cracking resistance and server resource limits.

BCrypt

Broad compatibility · Adaptive password hashing

BCrypt is widely supported and is especially useful when an application already uses it or needs broad compatibility with existing systems.

Configurable parameter: Work factor, commonly expressed as a logarithmic cost.

Increasing the cost increases computational effort. BCrypt implementations generally have a 72-byte password-input limit, which makes correct input handling important.

Trade-off: Its memory requirements are comparatively modest, and the input-length limitation must be accounted for explicitly.

PBKDF2

Standards and compliance-oriented environments

PBKDF2 repeatedly applies a pseudorandom function to derive a password-based result. Its cost is primarily controlled through the iteration count and the selected underlying function.

It is a practical option when FIPS-validated implementations or specific enterprise compliance requirements matter.

Trade-off: It is not memory-hard in the same sense as Argon2id or scrypt, and its parameters must be selected according to current guidance.

scrypt

Memory-hard alternative

scrypt is designed to make password guessing costly in both computation and memory.

Configurable parameters: CPU/memory cost N, block size r, and parallelization p.

Trade-off: Memory consumption and implementation support must be considered when choosing parameters and planning capacity.

The algorithms solve the same broad password-storage problem, but their parameter models and operational characteristics differ. They are not interchangeable simply by choosing the same numeric cost.

3. How to select parameters

There is no universally optimal cost configuration for every server.

OWASP's current password-storage guidance gives these useful minimum reference configurations:

Algorithm OWASP reference guidance
Argon2id At least 19 MiB memory, 2 iterations and parallelism 1
scrypt At least N=217, r=8, p=1
BCrypt Work factor 10 or greater for legacy systems
PBKDF2-HMAC-SHA-256 At least 600,000 iterations when applicable

These are reference points from OWASP guidance, not universal production settings. Requirements, libraries, hardware and guidance can change. (OWASP Cheat Sheet Series)

A senior engineer should:

  1. Choose a supported, appropriate algorithm.
  2. Benchmark password verification on production-like hardware.
  3. Measure typical and tail latency.
  4. Measure CPU and memory consumption under concurrent login load.
  5. Consider how login traffic could be abused to exhaust resources.
  6. Record the selected parameters and define when they should be reviewed.

For example, a memory-hard configuration that works for ten concurrent login requests may behave very differently when several hundred requests arrive simultaneously.

4. BCrypt's cost factor

BCrypt's work factor controls its computational cost. Its conventional cost structure grows approximately exponentially: increasing the work factor by one roughly doubles the core computational work, all else being equal.

For example, moving from cost 10 to cost 11 generally increases the work per hash by roughly a factor of two.

This is not an exact wall-clock prediction. Hardware, implementation details and concurrency affect actual performance.

The correct approach is to benchmark candidate values and choose the strongest practical setting that satisfies the system's latency and capacity requirements.

5. Password length and Unicode

Password validation needs more care than a simple minimum-length check.

Consider these inputs:

  • A short password.
  • A long passphrase.
  • A password containing non-English characters.
  • A password containing emoji.
  • An extremely large request designed to consume resources.

Length can mean different things:

  • Java UTF-16 code units.
  • Unicode code points.
  • UTF-8 bytes.

These are not always equal.

BCrypt's common 72-byte input limit is particularly important because a Java string containing 72 characters can exceed 72 UTF-8 bytes. Silent truncation can cause different passwords to be treated as equivalent by some implementations.

For a BCrypt-based application:

  • Enforce an input limit compatible with the exact encoder's documented behavior.
  • Make the limit clear to users.
  • Do not silently truncate passwords.
  • Do not introduce an improvised pre-hashing construction to bypass the limit.
  • Test international characters and long inputs explicitly.

If unrestricted long-password support is a requirement, evaluate an appropriate algorithm and implementation rather than assuming all password encoders handle arbitrary-length inputs identically. (OWASP Reference)

E. Java and Spring Boot password encoding

Spring Security provides the PasswordEncoder abstraction. It lets application code encode passwords and verify candidates without depending directly on a particular algorithm's implementation.

The two core operations are:

String encoded = passwordEncoder.encode(rawPassword);

boolean matches = passwordEncoder.matches(
        submittedPassword,
        encodedPasswordFromDatabase
);

These methods have different purposes:

  • encode(...) generates an encoded password representation for storage.
  • matches(...) checks whether a submitted password matches an existing encoded representation.

Do not write your own salt-generation or password-verification algorithm when a maintained password encoder is available.

1. BCryptPasswordEncoder

A direct BCrypt implementation looks like this:

import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.security.crypto.password.PasswordEncoder;

public class PasswordHashExample {

    public static void main(String[] args) {
        PasswordEncoder encoder = new BCryptPasswordEncoder(12);

        String rawPassword = "Example-Password-For-Testing";

        String encoded = encoder.encode(rawPassword);

        boolean correct = encoder.matches(rawPassword, encoded);
        boolean incorrect = encoder.matches("wrong-password", encoded);

        System.out.println("Correct password matches: " + correct);
        System.out.println("Wrong password matches: " + incorrect);
    }
}

The work factor of 12 is an illustrative setting, not a production recommendation without benchmarking.

For the example, the first verification should succeed and the second should fail.

Notice what the code does not do: it does not call encode again and compare the newly generated string with the stored string. BCrypt generates a salt, so a second encoding of the same password normally differs.

The matches method performs the appropriate verification.

2. Where is the salt stored?

BCrypt's encoded representation contains the information needed to verify the password, including the salt and work factor.

The application normally stores the complete encoded string in the database. It does not need a separate salt column when the chosen encoder embeds the required information in its representation.

A stored BCrypt value commonly has a structure resembling:

$2a$12$<salt-and-hash-data>

The exact version marker and representation depend on the implementation.

The cost factor and salt are not secrets. The security of the stored password depends on the properties of the algorithm and its parameters, not on hiding the algorithm's format.

3. PasswordEncoder interface

Spring Security's PasswordEncoder interface provides a consistent abstraction for password storage and verification. (Spring Docs)

Conceptually, its main methods are:

String encode(CharSequence rawPassword);

boolean matches(
        CharSequence rawPassword,
        String encodedPassword
);

This abstraction is valuable because business logic should not need to know the internal details of every supported algorithm.

For example, the registration service can depend on PasswordEncoder instead of constructing a new BCryptPasswordEncoder each time it registers a user.

That improves testability, configuration management and future migration.

4. DelegatingPasswordEncoder

DelegatingPasswordEncoder supports multiple password-hashing formats through an encoded string containing an algorithm identifier.

A stored value has the general form:

{id}encodedPassword

For example:

{bcrypt}$2a$12$...

The prefix tells Spring Security which configured encoder should verify the stored password.

This helps with password-hash migration because the database can contain hashes produced by different supported algorithms while new passwords use the selected current encoder. (Spring Docs)

Create the encoder as a Spring bean:

package com.example.security;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.crypto.factory.PasswordEncoderFactories;
import org.springframework.security.crypto.password.PasswordEncoder;

@Configuration
public class PasswordEncodingConfig {

    @Bean
    public PasswordEncoder passwordEncoder() {
        return PasswordEncoderFactories
                .createDelegatingPasswordEncoder();
    }
}

In the documented Spring Security factory configuration, the default encoding algorithm is BCrypt, with the algorithm identifier included in the stored value. Confirm the actual behavior against the Spring Security version pinned by your application.

Security Warning

Important: DelegatingPasswordEncoder is not itself a new hashing algorithm. It dispatches encoding and verification to the configured implementations.

Also, do not add insecure legacy encoders such as plaintext (noop) merely to make old records authenticate. Any legacy migration must be deliberate, with the old format accepted only when explicitly justified and with a plan to eliminate it.

5. Argon2id in Spring Security

Spring Security also provides an Argon2 encoder implementation. Availability and dependency requirements depend on the selected Spring Security version.

For the Spring Security 6.x generation, Argon2PasswordEncoder requires Bouncy Castle support. The encoder can be configured with explicit parameters, but those parameters must be chosen and benchmarked for the target environment.

Do not copy a cost configuration from a different library and assume it means the same thing in Spring Security.

The important engineering decision is to choose one intended password-hashing strategy, verify the required dependencies and configuration, and keep the application code dependent on PasswordEncoder.

F. Password-hash migration and rehashing

A password-hashing algorithm is not a permanent decision. Hardware becomes faster, recommendations evolve, and applications may need to change their password-storage strategy.

A good system must support these changes without requiring every user's plaintext password to be available.

1. Why migration is necessary

Suppose an application originally stored BCrypt hashes using work factor 10. Several years later, the team decides to increase the cost.

The application cannot simply decode the existing hashes and generate new ones. Password hashes are not designed to be reversed.

There are two main migration situations.

Situation A: The user logs in successfully.
The application now has the submitted password in memory and can use the stronger encoder to produce a new hash.

Situation B: The user never logs in again.
The application cannot rehash the original password because it does not know it. It must continue to support the existing hash safely for a transition period or require an appropriate password-reset process.

2. Rehashing after successful authentication

Spring Security's PasswordEncoder provides upgradeEncoding(String encodedPassword), which allows an encoder to indicate whether a stored representation should be upgraded.

A conceptual flow is:

Rehashing & Encoding Upgrade Flow
flowchart TD A["Retrieve stored password hash"] --> B["Verify submitted password"] B --> C{"Password matches?"} C -- No --> D["Reject login"] C -- Yes --> E{"Hash needs upgrade?"} E -- No --> F["Continue successful login processing"] E -- Yes --> G["Generate new hash using current policy"] G --> H["Update stored hash safely"] H --> F

A successful password match is important: the application must not replace a user's stored hash with a new hash of an unverified password.

3. Handling concurrent login attempts

Consider two simultaneous login requests for the same account:

  1. Both retrieve the old password hash.
  2. Both verify the submitted password successfully.
  3. Both determine that the hash should be upgraded.
  4. Both generate a new encoded hash.

If the submitted passwords are identical, both newly generated hashes should verify the same password. However, a concurrent password change creates a more serious race.

Suppose one request verifies the old password while another changes the account password. The first request must not overwrite the newer password hash with a hash of the old password.

A robust design needs a concurrency policy. Depending on the persistence layer, this may involve optimistic locking, a conditional database update against the previously observed hash, or a transactional account-version check.

For example, a conditional update can conceptually require that the stored hash still equals the value originally verified:

UPDATE users
SET password_hash = :newHash
WHERE id = :userId
  AND password_hash = :previousHash;

The service should check the number of affected rows. Zero affected rows means the record changed before the update, so the service must not assume the upgrade succeeded.

This illustrates a general principle: security-sensitive state changes must account for concurrency, not just successful single-request execution.

4. Migration from a legacy format

DelegatingPasswordEncoder is useful when multiple formats must coexist.

A migration plan should define:

  • Which legacy formats are currently present.
  • Which implementations are permitted to verify them.
  • Which format is used for new password hashes.
  • Whether successful login should trigger rehashing.
  • What happens to users who never return.
  • When legacy verification support will be removed.

Do not automatically wrap a weak legacy hash in a modern algorithm and declare the problem solved. Layering hashes can preserve weaknesses in the original construction. OWASP recommends migrating to direct password hashes of the original password when it becomes available during successful authentication. (OWASP Reference)

G. Designing the user database schema

A secure authentication implementation needs a database model that supports correct behavior and prevents inconsistent account records.

1. Example user entity

For this lesson, assume a relational database and Spring Data JPA.

A minimal user record may contain:

Field Purpose
id Stable internal user identifier
email Login identifier, if email-based login is chosen
password_hash Encoded password-hashing result
email_verified Whether the email-verification process has completed
created_at Account creation timestamp
password_changed_at Time of the last password change

The schema can evolve as the application introduces account states and other requirements.

The important constraint is that the password field contains the encoded hash, not the original password.

2. Why a unique email constraint matters

Application-level checks alone are not enough to guarantee uniqueness.

Imagine two concurrent registration requests:

  1. Request A checks whether alice@example.com exists.
  2. Request B checks the same email before A has committed.
  3. Both requests see no existing account.
  4. Both attempt to insert the same email.

A database unique constraint prevents both records from being committed.

Example SQL:

CREATE TABLE users (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    email VARCHAR(320) NOT NULL,
    password_hash VARCHAR(255) NOT NULL,
    email_verified BOOLEAN NOT NULL DEFAULT FALSE,
    created_at TIMESTAMP NOT NULL,
    password_changed_at TIMESTAMP
);

CREATE UNIQUE INDEX uq_users_email
    ON users (email);

This is illustrative SQL; identity syntax, case-insensitive uniqueness and timestamp types vary by database.

For an email-based login system, the application should also define how email addresses are normalized and compared. The database's collation and the application's normalization policy must agree.

Do not apply arbitrary transformations to email addresses that could change their meaning. A unique index on a case-sensitive column may not enforce the same policy as case-insensitive login.

3. Store only what you need

The database should not contain:

  • Plaintext passwords.
  • Passwords written to diagnostic fields.
  • Reversible copies of passwords.
  • Unnecessary copies of authentication secrets.

The encoded hash is sufficient for password verification.

Account recovery may require separate verification tokens, but those should be stored and handled according to their own security requirements, not by reusing the password-hash column.

2. The user entity

package com.example.account.entity;

import jakarta.persistence.*;
import java.time.Instant;

@Entity
@Table(
    name = "users",
    uniqueConstraints = @UniqueConstraint(
        name = "uq_users_email",
        columnNames = "email"
    )
)
public class User {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 320)
    private String email;

    @Column(name = "password_hash", nullable = false, length = 255)
    private String passwordHash;

    @Column(name = "email_verified", nullable = false)
    private boolean emailVerified = false;

    @Column(name = "created_at", nullable = false)
    private Instant createdAt;

    protected User() {
        // Required by JPA.
    }

    public User(String email, String passwordHash) {
        this.email = email;
        this.passwordHash = passwordHash;
        this.createdAt = Instant.now();
    }

    public Long getId() {
        return id;
    }

    public String getEmail() {
        return email;
    }

    public String getPasswordHash() {
        return passwordHash;
    }

    public void setPasswordHash(String passwordHash) {
        this.passwordHash = passwordHash;
    }

    public boolean isEmailVerified() {
        return emailVerified;
    }

    public void setEmailVerified(boolean emailVerified) {
        this.emailVerified = emailVerified;
    }

    public Instant getCreatedAt() {
        return createdAt;
    }
}

Notice that the entity exposes passwordHash, not a plaintext password field.

In a production application, use schema migrations such as Flyway or Liquibase to manage database changes explicitly. The entity annotation alone should not be treated as proof that the production database has the intended constraints.

3. Repository

package com.example.account.repository;

import com.example.account.entity.User;
import org.springframework.data.jpa.repository.JpaRepository;

import java.util.Optional;

public interface UserRepository extends JpaRepository<User, Long> {

    Optional<User> findByEmail(String email);

    boolean existsByEmail(String email);
}

The repository encapsulates persistence operations.

The service will use it to check for existing accounts, create new users and retrieve users for login.

The database constraint remains essential even though existsByEmail is available.

4. Request and response DTOs

A DTO (Data Transfer Object) defines the fields accepted or returned by an API. It prevents the application from exposing its persistence entity directly.

Registration request:

package com.example.account.dto;

import jakarta.validation.constraints.Email;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.Size;

public record RegisterRequest(
    @NotBlank
    @Email
    @Size(max = 320)
    String email,

    @NotBlank
    @Size(min = 12, max = 72)
    String password
) {}

Login request:

package com.example.account.dto;

import jakarta.validation.constraints.Email;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.Size;

public record LoginRequest(
    @NotBlank
    @Email
    @Size(max = 320)
    String email,

    @NotBlank
    @Size(max = 72)
    String password
) {}

Account response:

package com.example.account.dto;

public record AccountResponse(
    Long id,
    String email,
    boolean emailVerified
) {}

Important input-limit qualification

The 72 limit here is a conservative example for a BCrypt-based design and is expressed in Java's @Size character-count semantics, not UTF-8 bytes. It is not a sufficient implementation of BCrypt's byte limit for every Unicode input. Production code must enforce the exact encoder's input constraints and avoid silent truncation. If using Argon2id or another encoder, define and enforce an appropriate request-size and password-length policy for that implementation.

Password validation should reject invalid inputs without modifying the password unexpectedly. Avoid trimming, lowercasing or otherwise normalizing the password unless the system has an explicitly justified and consistently implemented policy.

5. Account service: registration

The service is responsible for business rules around account creation.

package com.example.account.service;

import com.example.account.dto.AccountResponse;
import com.example.account.dto.RegisterRequest;
import com.example.account.entity.User;
import com.example.account.repository.UserRepository;
import org.springframework.dao.DataIntegrityViolationException;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import java.util.Locale;

@Service
public class AccountService {

    private final UserRepository userRepository;
    private final PasswordEncoder passwordEncoder;

    public AccountService(
            UserRepository userRepository,
            PasswordEncoder passwordEncoder) {
        this.userRepository = userRepository;
        this.passwordEncoder = passwordEncoder;
    }

    @Transactional
    public AccountResponse register(RegisterRequest request) {
        String email = normalizeEmail(request.email());

        if (userRepository.existsByEmail(email)) {
            throw new EmailAlreadyExistsException();
        }

        String passwordHash =
                passwordEncoder.encode(request.password());

        User user = new User(email, passwordHash);

        try {
            User saved = userRepository.saveAndFlush(user);

            return new AccountResponse(
                    saved.getId(),
                    saved.getEmail(),
                    saved.isEmailVerified()
            );
        } catch (DataIntegrityViolationException ex) {
            // Do not expose database internals.
            // This catch is only appropriate if this operation is
            // expected to handle the specific uniqueness race.
            throw new RegistrationConflictException();
        }
    }

    private String normalizeEmail(String email) {
        return email.trim().toLowerCase(Locale.ROOT);
    }
}

The example uses lowercasing as an explicit application policy for email identifiers. Real email-address comparison rules can be more nuanced; define and enforce one consistent policy across registration, login and the database.

The custom exceptions are application-defined and would need to be implemented.

Why saveAndFlush?

A database constraint may be checked when the SQL statement is executed or when the transaction is committed, depending on the database and constraint configuration.

saveAndFlush requests that pending changes be flushed before the method returns, allowing many immediate constraint violations to be handled within this operation. It does not guarantee that every possible commit-time failure is caught at that exact line.

The production implementation must distinguish a duplicate-email conflict from unrelated database failures. Do not translate every database exception into "email already exists."

6. Account service: password verification

@Transactional(readOnly = true)
public AccountResponse authenticate(LoginRequest request) {
    String email = normalizeEmail(request.email());

    User user = userRepository.findByEmail(email)
            .orElseThrow(InvalidCredentialsException::new);

    boolean matches = passwordEncoder.matches(
            request.password(),
            user.getPasswordHash()
    );

    if (!matches) {
        throw new InvalidCredentialsException();
    }

    return new AccountResponse(
            user.getId(),
            user.getEmail(),
            user.isEmailVerified()
    );
}

This method belongs inside the AccountService class shown earlier.

It demonstrates password verification, but a successful password match is not the same as maintaining an authenticated login across future requests.

In this topic, we are deliberately not adding a session cookie or token. Topic 3 will explain server-side sessions, and Topic 6 will cover JWT-based authentication.

A real application must connect successful credential verification to its chosen authentication lifecycle before treating later requests as authenticated.

7. Controller

package com.example.account.controller;

import com.example.account.dto.AccountResponse;
import com.example.account.dto.LoginRequest;
import com.example.account.dto.RegisterRequest;
import com.example.account.service.AccountService;
import jakarta.validation.Valid;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;

@RestController
@RequestMapping("/api/accounts")
public class AccountController {

    private final AccountService accountService;

    public AccountController(AccountService accountService) {
        this.accountService = accountService;
    }

    @PostMapping("/register")
    public ResponseEntity<AccountResponse> register(
            @Valid @RequestBody RegisterRequest request) {

        AccountResponse response = accountService.register(request);

        return ResponseEntity.status(HttpStatus.CREATED)
                .body(response);
    }

    @PostMapping("/login")
    public ResponseEntity<AccountResponse> login(
            @Valid @RequestBody LoginRequest request) {

        AccountResponse response = accountService.authenticate(request);

        return ResponseEntity.ok(response);
    }
}

The controller delegates account logic to the service rather than implementing password verification itself.

The registration response contains account metadata but never the password or encoded password hash.

The login response demonstrates successful credential verification only. It must not be interpreted as a complete production login mechanism because this example does not establish persistent authenticated state.

8. Error handling and generic login errors

Define application exceptions:

package com.example.account.service;

public class InvalidCredentialsException
        extends RuntimeException {

    public InvalidCredentialsException() {
        super("Invalid credentials");
    }
}

A corresponding registration conflict exception can be used for the documented registration policy.

The error handler should return a safe, consistent response:

package com.example.account.exception;

import com.example.account.service.InvalidCredentialsException;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;

import java.util.Map;

@RestControllerAdvice
public class ApiExceptionHandler {

    @ExceptionHandler(InvalidCredentialsException.class)
    public ResponseEntity<Map<String, String>> invalidCredentials(
            InvalidCredentialsException ex) {

        return ResponseEntity.status(HttpStatus.UNAUTHORIZED)
                .body(Map.of(
                        "error",
                        "Invalid email or password"
                ));
    }
}

The message is the same whether the email is unknown or the password is incorrect.

This helps reduce account enumeration through response content. However, identical text alone is insufficient if the status code, response shape, timing or other observable behavior reveals whether the account exists.

The exception handler also does not replace appropriate handling for malformed requests, duplicate registrations, database outages or unexpected server errors.

I. Registration and login: request walkthroughs

Let's examine how the application behaves at the HTTP level.

1. Successful registration

Request:

POST /api/accounts/register
Content-Type: application/json

{
  "email": "alice@example.com",
  "password": "Example-Password-For-Testing"
}

Processing sequence:

  1. Spring MVC deserializes the JSON into RegisterRequest.
  2. @Valid triggers request validation.
  3. The controller invokes AccountService.register.
  4. The service normalizes the email according to the application's policy.
  5. The repository checks for an existing account.
  6. The configured PasswordEncoder encodes the password.
  7. The entity stores the encoded hash.
  8. The database enforces its uniqueness constraint.
  9. The API returns account metadata without the password or hash.

Expected response:

HTTP/1.1 201 Created
Content-Type: application/json

{
  "id": 101,
  "email": "alice@example.com",
  "emailVerified": false
}

The example does not yet send a verification email. That is a separate account-lifecycle operation.

2. Registration with a duplicate email

If an account already exists, the application rejects the registration according to its registration policy.

A user-friendly error might be:

HTTP/1.1 409 Conflict
Content-Type: application/json

{
  "error": "An account cannot be created with these details"
}

The precise message depends on the product's account-enumeration policy.

For a public registration endpoint, explicitly stating that an email exists may reveal account membership. Some applications deliberately return a generic response for registration and recovery requests to reduce this risk.

3. Successful password verification

Request:

POST /api/accounts/login
Content-Type: application/json

{
  "email": "alice@example.com",
  "password": "Example-Password-For-Testing"
}

The service retrieves the user's encoded hash and calls:

passwordEncoder.matches(
    submittedPassword,
    storedPasswordHash
);

If the password matches, credential verification succeeds.

The earlier controller returns account metadata, but this response alone does not create an authenticated session or issue a token. In a real application, the verified credentials must feed into the authentication mechanism assigned to a later topic.

4. Incorrect password

The API should return a generic authentication failure:

HTTP/1.1 401 Unauthorized
Content-Type: application/json

{
  "error": "Invalid email or password"
}

The same public message should be used when the email is unknown.

Avoid messages such as:

  • "This email does not exist."
  • "The account exists, but the password is incorrect."
  • "The account is registered but not verified."

Some of those distinctions may be necessary for product behavior, but exposing them publicly requires a deliberate account-enumeration risk assessment.

5. Malformed registration input

Example:

{
  "email": "not-an-email",
  "password": ""
}

The validation layer should reject this request before account creation.

A validation error may return HTTP 400 Bad Request, with a controlled response describing the invalid fields.

Validation should not expose the password or include its value in error messages or logs.

6. Database unavailable

If the database cannot be reached, the service cannot reliably create or retrieve an account.

The application should return an appropriate server-side failure, avoid leaking database details, and record enough safe diagnostic information for investigation.

It must not silently bypass password verification or claim that a registration succeeded when persistence has failed.

J. Account-enumeration and brute-force protection

Password verification is only one part of login security. Attackers may target the account endpoint itself to discover valid accounts or consume server resources.

1. Account enumeration

Account enumeration occurs when an attacker can determine whether a particular account exists through observable application behavior.

Potential signals include:

  • Different error messages.
  • Different HTTP status codes.
  • Different response structures.
  • Measurably different response times.
  • Different throttling behavior.
  • Different recovery or registration responses.

A generic message is a useful defense, but it is not sufficient by itself.

Timing differences

Consider these two code paths:

Unknown email
    -> database lookup
    -> immediate failure

Existing email with wrong password
    -> database lookup
    -> expensive password verification
    -> failure

The second path may take noticeably longer because password hashing is intentionally expensive.

An attacker who can perform enough measurements may infer whether an account exists.

One possible mitigation is to perform a verification against a precomputed dummy encoded hash when the account is absent. This reduces the obvious timing difference between the two paths.

Conceptually:

User user = userRepository.findByEmail(email).orElse(null);

String hashToCheck = user != null
        ? user.getPasswordHash()
        : dummyEncodedPassword;

boolean matches = passwordEncoder.matches(
        request.password(),
        hashToCheck
);

if (user == null || !matches) {
    throw new InvalidCredentialsException();
}

dummyEncodedPassword must be a valid encoded password hash generated in advance using the intended encoder and comparable cost parameters. It should not be generated for every failed login.

This is a conceptual fragment, not a complete authentication service. The implementation must also consider missing or malformed stored hashes, rate limits and the behavior of legacy encoders.

A dummy verification can reduce a major timing difference, but it does not guarantee constant-time end-to-end behavior. Database access, caching, network latency and other processing can still differ.

2. Login throttling and rate limiting

Password verification can be computationally expensive. An attacker can exploit that expense even without successfully guessing a password.

For example, an endpoint that accepts thousands of simultaneous password checks can consume substantial CPU and memory.

A production design should define:

  • Maximum sustained request rates.
  • Burst limits.
  • Per-account or per-identifier attempt policies.
  • Additional controls for suspicious source patterns.
  • How throttling state is shared across application instances.
  • What happens when the rate-limiting dependency fails.

Per-IP limits alone are insufficient because attackers can distribute requests across multiple IP addresses. Per-account limits alone can also be abused to deny service to a victim.

The design must balance attack resistance against legitimate users behind shared networks.

3. Account lockout trade-offs

A naive policy locks an account permanently after five incorrect passwords.

An attacker who knows the victim's email can intentionally submit five incorrect guesses and deny the victim access.

Therefore, account lockout is not automatically safer than throttling.

A better policy depends on the threat model and may combine progressive delays, request limits, temporary restrictions, additional verification and account-recovery procedures.

Any state used for throttling should be designed for multiple application instances if the system is horizontally scaled.

4. Resource exhaustion through expensive password verification

The work factor protects against offline cracking, but the same computational cost applies to legitimate login verification.

This creates a security trade-off:

  • A stronger password-hashing configuration increases offline attack cost.
  • A high volume of online login attempts can consume application resources.
  • A larger number of concurrent requests increases the memory and CPU needed for verification.

Mitigate this with layered request limits, bounded concurrency, appropriate timeouts and monitoring. Do not simply reduce password-hashing cost to accommodate unbounded traffic.

K. Password reset, email verification and account recovery

Account recovery is part of authentication security because it creates another way to gain control of an account.

A perfectly implemented login endpoint can still be undermined by a password-reset flow that accepts predictable or reusable tokens.

1. Password reset: required security properties

A password-reset mechanism should have these properties:

  • The reset request does not disclose whether an account exists.
  • Reset tokens are generated using a cryptographically secure random generator.
  • Tokens are bound to the intended account and reset operation.
  • Tokens expire after a defined, limited period.
  • Tokens are single-use.
  • Token verification and consumption are protected against concurrent reuse.
  • Tokens are not logged or unnecessarily exposed.
  • Successful reset invalidates the reset token and updates the stored password hash.
  • The user receives an appropriate notification of the change.

A reset token is not a password hash. It is a temporary bearer secret used to authorize a particular recovery operation. Its lifecycle must be designed accordingly.

2. Recommended reset flow

Secure Password Reset Lifecycle
sequenceDiagram participant U as User participant A as Account API participant D as Database participant M as Email Service U->>A: Request password reset A->>A: Return generic response A->>D: Create token record if account is eligible A->>M: Send reset link U->>A: Submit reset token and new password A->>D: Verify token, expiry and unused state A->>A: Hash new password A->>D: Update password and consume token atomically A-->>U: Return success or safe failure

The flow is conceptual. Email delivery, persistence and transaction handling must be designed for the selected infrastructure.

3. Generating a reset token

A reset token should be unpredictable and sufficiently long.

import java.security.SecureRandom;
import java.util.Base64;

public final class ResetTokenGenerator {

    private static final SecureRandom RANDOM = new SecureRandom();

    private ResetTokenGenerator() {}

    public static String generate() {
        byte[] bytes = new byte[32];
        RANDOM.nextBytes(bytes);

        return Base64.getUrlEncoder()
                .withoutPadding()
                .encodeToString(bytes);
    }
}

This produces 32 random bytes, represented as a URL-safe Base64 string.

The raw token should be sent only through the intended recovery channel. It should not be written to application logs.

4. Store a hash of the reset token

If the database stores the raw reset token, a database leak may allow an attacker to use any unexpired token immediately.

For a high-entropy random token, a fast cryptographic hash such as SHA-256 can be appropriate for token lookup because the token is randomly generated with sufficient entropy. This is a different use case from human-chosen passwords.

Conceptually:

th = SHA256(t)

Store the token hash, account ID, expiry and consumption state. When a user presents the token, calculate its hash and look up the matching record.

Do not reuse the raw token after verification.

5. Atomic single-use consumption

Suppose two concurrent requests submit the same reset token.

If both requests independently check that the token is unused and then proceed, both might attempt a password change.

The check and consumption need to be atomic.

A design can use a database transaction with a conditional update, such as:

UPDATE password_reset_tokens
SET consumed_at = CURRENT_TIMESTAMP
WHERE token_hash = :tokenHash
  AND consumed_at IS NULL
  AND expires_at > CURRENT_TIMESTAMP;

The application must check that exactly one row was affected before allowing the password change to proceed, and the token consumption and password update must be committed atomically.

The complete transaction also needs to verify the intended account and handle database failures safely.

6. Email verification

Email verification establishes that the user can receive messages at the address they supplied. It does not prove the user's real-world identity.

A verification flow should use a securely generated token, an expiry policy, and single-use consumption. It should also define what unverified users are permitted to do.

For example, a portfolio application might allow a user to create an account but restrict sensitive account-recovery operations until the email has been verified.

The correct policy depends on the application's requirements.

7. Password changes and existing authentication state

When a user changes their password, the application should:

  1. Verify the current password when appropriate.
  2. Validate the new password.
  3. Encode the new password using the current password-storage policy.
  4. Update the database safely.
  5. Update the password-change timestamp.
  6. Notify the user through an appropriate channel.
  7. Apply the documented policy for existing authenticated access.

A password change may need to invalidate existing sessions or other authentication credentials. The detailed mechanics depend on the authentication architecture and are reserved for Topics 3 and 6.

Do not claim that changing the password automatically invalidates all existing access unless the system actually implements that behavior.

L. Testing and verification

A secure account system must be tested for both successful behavior and failure behavior.

1. Unit tests for password encoding

import org.junit.jupiter.api.Test;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;

import static org.junit.jupiter.api.Assertions.*;

class PasswordEncoderTest {

    private final PasswordEncoder encoder =
            new BCryptPasswordEncoder(10);

    @Test
    void encodedPasswordMatchesOriginal() {
        String raw = "Example-Password-For-Testing";
        String encoded = encoder.encode(raw);

        assertTrue(encoder.matches(raw, encoded));
    }

    @Test
    void wrongPasswordDoesNotMatch() {
        String encoded = encoder.encode(
                "Example-Password-For-Testing"
        );

        assertFalse(encoder.matches("wrong-password", encoded));
    }

    @Test
    void samePasswordCanProduceDifferentHashes() {
        String raw = "Example-Password-For-Testing";

        String first = encoder.encode(raw);
        String second = encoder.encode(raw);

        assertNotEquals(first, second);

        assertTrue(encoder.matches(raw, first));
        assertTrue(encoder.matches(raw, second));
    }
}

The cost factor is deliberately modest to keep the illustrative test relatively quick. Production configuration should be selected separately using representative benchmarks.

These tests prove basic encoding and verification behavior. They do not prove that the database, controller, recovery flow or deployment is secure.

4. Recovery test cases

  • Expired reset token is rejected.
  • Already-consumed reset token is rejected.
  • Invalid token is rejected.
  • A reset token cannot be used successfully twice.
  • Concurrent attempts cannot consume the same token twice.
  • A failed database transaction does not leave a password change partially committed.
  • The public reset-request response does not reveal whether an account exists.
  • Raw reset tokens do not appear in logs.
  • The stored password after reset is an encoded hash.

5. Integration tests

Use the actual repository, persistence configuration and service layer in integration tests.

Verify database constraints rather than relying only on mocked repository responses.

For concurrency-sensitive behavior, execute competing requests or transactions and verify the final database state.

Spring Boot's testing support can help exercise these flows. Detailed MockMvc and Spring Security testing patterns will be covered in the later Spring Security and production-testing topics.

M. Production readiness

1. Password-hashing capacity planning

Password verification is intentionally expensive. Treat it as a resource-intensive operation.

Measure:

  • Encoding and verification latency.
  • CPU and memory consumption.
  • Login throughput.
  • Tail latency under concurrent load.
  • Behavior during traffic spikes.
  • The impact of rate limiting and bounded concurrency.

If a server can perform R verifications per second and receives L login requests per second, then sustained login traffic above available verification capacity creates a queue or causes requests to fail.

The exact relationship depends on the server architecture and available resources, but the operational principle is straightforward: password verification needs explicit capacity planning.

2. Sensitive data handling

Password-related data requires careful treatment across the entire application lifecycle.

Data Handling principle
Plaintext password Use only when needed for verification or encoding; never persist or log it
Encoded password hash Store in a restricted database field; never return it through ordinary APIs
Password-reset token Send only through the intended channel; avoid storing the raw token
Email-verification token Use a limited lifetime and single-use policy
Login failure metadata Log only what is needed for security analysis and protect it appropriately

A hash is not the plaintext password, but it remains sensitive authentication-related data. If stolen, it can enable offline password guessing.

3. Account recovery and incident response

Production procedures should cover:

  • A suspected password database leak.
  • A compromised reset token.
  • A large spike in failed login attempts.
  • A compromised user account.
  • A password-hashing configuration that is no longer adequate.
  • A database migration that leaves incompatible password-hash formats.

The incident response plan should specify how to assess impact, contain the issue, preserve useful evidence, communicate with affected users and recover safely.

4. Database and transaction integrity

Account operations should preserve invariants:

  • Each normalized login identifier has the intended uniqueness guarantee.
  • A successful registration persists the account exactly once.
  • A password change does not overwrite a newer concurrent change.
  • A reset token cannot be consumed twice.
  • Failed operations do not report success.
  • Password hashes are updated consistently with their associated account state.

These are security properties as well as data-integrity properties.

N. How a Senior Engineer Thinks About This

Before selecting a password encoder or implementing a login endpoint, an experienced engineer asks the following questions.

1. Algorithm selection

  • Is the algorithm appropriate for new password storage or is it being retained for legacy compatibility?
  • Are the parameters consistent with current security guidance?
  • Has the implementation's password-input limit been verified?
  • Have latency and memory use been benchmarked on target hardware?
  • Can the algorithm and its parameters be upgraded later?

2. Account lifecycle

  • How are duplicate registrations handled under concurrency?
  • Does login expose whether an account exists?
  • What limits repeated authentication attempts?
  • How are reset tokens generated, stored, expired and consumed?
  • What happens to existing authentication state after a password change?
  • Can account recovery be abused to deny service to legitimate users?

3. Failure behavior

  • What happens if the database is unavailable?
  • What happens if a stored password hash is malformed?
  • What happens if email delivery fails after a reset request?
  • What happens if two password changes race?
  • What happens if an old hash format is no longer supported?

4. Evidence and verification

  • Are password hashes demonstrably stored instead of plaintext?
  • Do negative tests prove that incorrect passwords fail?
  • Can concurrent registration violate the uniqueness invariant?
  • Can a reset token be used twice?
  • Does the system remain stable under the expected login load?
  • Can operators investigate attacks without logging secrets?

P. Hands-on exercise — Secure Account Authentication Service

Practical assignment

Build a production-conscious registration and login service

Implement the service using Java 17+, Spring Boot, Spring Data JPA, a relational database, and Spring Security's password-encoding APIs.

The goal is to demonstrate secure password storage and account-lifecycle behavior, not to build a complete token or session system.

Functional requirements

  • Register users with a unique email address and a password that satisfies the defined input policy.
  • Store only the encoded password hash.
  • Verify passwords correctly during login.
  • Return generic authentication failures.
  • Implement password-reset requests and single-use reset tokens.
  • Support email verification with expiring verification tokens.
  • Document how password changes affect existing authentication state.

Security requirements

  • Use a maintained password encoder with an explicitly chosen configuration.
  • Enforce database uniqueness under concurrent registration.
  • Apply login throttling and account-enumeration defenses.
  • Never log or return passwords, encoded password hashes or raw reset tokens.
  • Handle database failures without reporting false success.
  • Prevent a reset token from being consumed more than once.
  • Define a migration strategy for future password-hashing changes.

Acceptance criteria

  • Valid registration persists an encoded password hash.
  • Correct credentials pass verification; incorrect credentials fail.
  • Unknown accounts and wrong passwords receive equivalent public authentication failures.
  • Competing registration requests cannot create duplicate accounts.
  • Expired, invalid and previously consumed reset tokens are rejected.
  • Concurrent reset requests cannot both consume the same token successfully.
  • Integration tests cover the database constraints and transaction behavior.
  • Load tests demonstrate acceptable login latency and resource usage under expected traffic.

Suggested implementation order

  1. Implement the user entity, schema and password encoder.
  2. Implement registration and its validation tests.
  3. Implement password verification and generic errors.
  4. Add throttling and account-enumeration defenses.
  5. Add reset-token storage, expiry and atomic consumption.
  6. Add email verification, migration planning and concurrency tests.

Do not implement every component in one large service method. Keep account rules, persistence operations, password encoding and HTTP response handling separate enough to test independently.

Q. Topic recap

1. The most important concepts

  • Passwords should be stored using an appropriate password-hashing algorithm, not in plaintext or reversibly encrypted form.
  • Salts prevent straightforward reuse of precomputed results and make identical passwords produce different stored hashes.
  • Work factors increase the cost of offline password guessing but also affect legitimate login latency.
  • Argon2id, BCrypt, PBKDF2 and scrypt have different properties, parameter models and compatibility considerations.
  • PasswordEncoder.encode() creates an encoded password representation; matches() verifies a candidate password.
  • DelegatingPasswordEncoder supports multiple explicitly configured password formats and can facilitate migration.
  • Database constraints are necessary for correctness under concurrency.
  • Generic error messages help reduce account enumeration, but timing and other observable behavior matter too.
  • Password-reset and email-verification tokens need secure generation, limited lifetimes and single-use handling.
  • Password changes and hash upgrades must account for concurrent state changes.
  • Production readiness requires capacity planning, safe data handling, monitoring and negative testing.
