Topic 3 — Cookies and Server-Side Sessions

Backend Engineering & Application Security · Senior Engineer Study Notes · Java 17+ / Spring Boot

The central question in this topic is:
How can a server recognize the same user across multiple HTTP requests without asking the user to enter their password every time?

The answer is the combination of a server-side session and a mechanism for carrying a session identifier between requests, commonly a browser cookie.

This is a foundational backend concept. Before learning JWT and stateless authentication in Topic 6, you should understand how traditional session-based authentication works, where its state lives, how browsers send cookies, and how session security can fail.

We will build a Java/Spring Boot mental model, examine the internal request lifecycle, and design a secure session-based login system for a financial application.

A. Topic scope and learning objectives

By the end of this topic, you should be able to:

  • Explain why HTTP is stateless and why applications use sessions.
  • Distinguish the session identifier from the actual session data.
  • Trace session creation, lookup, expiration, logout and invalidation.
  • Explain how JSESSIONID and browser cookies work together.
  • Understand HttpOnly, Secure, SameSite, Path, Domain, Max-Age and expiration.
  • Explain session fixation and session hijacking, including their differences.
  • Design session-ID rotation after authentication.
  • Understand concurrent sessions and session limits.
  • Compare in-memory session storage with distributed storage such as Redis.
  • Explain why cookie-based authentication creates CSRF considerations.
  • Evaluate remember-me functionality and its security trade-offs.
  • Implement and test a basic session-based login system using Java and Spring Boot.

B. Mental model: HTTP, cookies and sessions

1. Why sessions exist

HTTP requests are independent at the protocol level. A server does not automatically remember that two requests came from the same user merely because they came from the same browser.

Consider these requests:

GET /api/portfolio HTTP/1.1
Host: app.example.com
GET /api/portfolio HTTP/1.1
Host: app.example.com

Without some additional mechanism, the server cannot infer that the second request belongs to the same authenticated user as the first.

The application needs a way to associate a later request with previously established authentication state.

A session provides that association.

2. Session versus cookie

This is the most important distinction in the topic.

Session — server-side state

The session contains data maintained by the server, potentially including the authenticated user's identity, session metadata and other application state.

Cookie — browser-side storage and transport

A cookie can carry a session identifier between the browser and server. The identifier lets the server locate the corresponding session.

A cookie is not the session itself.

For example, a browser may store:

Set-Cookie: JSESSIONID=opaque-random-value; Path=/; HttpOnly; Secure; SameSite=Lax

The value opaque-random-value is a placeholder. A real session identifier must be generated securely and should not encode sensitive information.

The server associates the identifier with server-side state. The browser ordinarily sends the cookie back on subsequent requests that match the cookie's scope and other sending rules.

The browser does not need to know the session's internal data.

3. The mental model

Imagine a bank's customer-support desk.

  • The server-side session is the bank's internal record of an authenticated interaction.
  • The session identifier is a reference used to retrieve that record.
  • The cookie is the envelope through which the browser carries that reference.

Possessing a valid reference can allow someone to act within the associated session. Therefore, the session identifier is a sensitive bearer credential even though it is not the user's password.

The analogy has a limitation: real session identifiers are cryptographic values, not predictable account numbers, and the application must validate the request and apply its security policy.

4. What a session should and should not contain

A session may contain:

  • A reference to the authenticated principal.
  • Authentication state or related metadata.
  • Creation and last-access timestamps.
  • Application-specific transient state.
  • Security-related metadata needed by the session implementation.

It should not ordinarily contain:

  • Plaintext passwords.
  • Raw password-reset tokens.
  • Unnecessary copies of sensitive financial records.
  • Long-lived secrets that could be avoided.
  • Large amounts of data that should live in the database.

Prefer storing a stable user identifier and retrieving authoritative business data when needed. Keeping stale copies of permissions or account information in a session can introduce consistency and security problems.

C. Session lifecycle and internal execution

1. Creating a session

A session can be created when the application needs to maintain server-side state. In a Java Servlet application, HttpServletRequest.getSession() retrieves the current session or creates one if it does not exist.

Compare:

HttpSession session = request.getSession();

with:

HttpSession session = request.getSession(false);

The difference matters:

  • getSession() returns an existing session or creates a new one.
  • getSession(false) returns the existing session or null if none exists.

An authentication check should not accidentally create a fresh session for every unauthenticated request when it only needs to inspect an existing session.

For example:

HttpSession session = request.getSession(false);

if (session == null) {
    // No existing session.
    // Handle the unauthenticated request.
}

This avoids unnecessary session creation, although the application must still determine whether the existing session represents an authenticated user.

2. The complete request lifecycle

Consider a customer signing in to a portfolio application.

Complete Session Request Lifecycle
sequenceDiagram participant B as Browser participant A as Java Application participant S as Session Store participant D as Database B->>A: POST /login with credentials A->>D: Retrieve user and stored password hash D-->>A: User record A->>A: Verify submitted password A->>S: Create or rotate authenticated session S-->>A: Session state A-->>B: Login success and Set-Cookie B->>A: GET /portfolio with session cookie A->>S: Resolve session identifier S-->>A: Authenticated session state A->>D: Retrieve portfolio data D-->>A: Portfolio data A-->>B: Authorized response

This diagram shows the conceptual flow. In a Spring Security application, authentication and session persistence are coordinated by framework components; a manually implemented servlet flow does not automatically acquire all those protections.

The important sequence is:

  1. The application verifies the credentials.
  2. The authenticated state is established server-side.
  3. The browser receives the session identifier.
  4. The browser sends that identifier with subsequent matching requests.
  5. The server resolves the session and determines whether the request has an authenticated context.
  6. The application performs the requested business operation.
  7. The session expires or is explicitly invalidated when appropriate.

A session cookie alone is not proof that the current request is authorized. The identifier must resolve to valid session state, and the application must enforce its access policy.

3. Where does session state live?

The storage location depends on the application's design.

Browser
Holds the session identifier in a cookie and sends it according to cookie rules. It should not hold the authoritative server-side session record.

Application process
May hold session data in memory in a simple deployment. This is easy to operate initially, but session state may disappear when the process restarts and may not be available to other application instances.

Shared session store
Multiple application instances can access a common session repository, such as Redis, through a suitable session-management integration. This supports horizontal scaling but introduces dependency availability, latency, serialization, consistency and operational considerations.

The session identifier is the reference. The session store contains the associated state.

This separation allows the application to invalidate a session on the server even when the browser still possesses a copy of the old identifier.

D. Cookie attributes and browser behavior

Cookies are defined through the HTTP Set-Cookie response header and subsequently sent through the Cookie request header when applicable.

A server might respond with:

Set-Cookie: JSESSIONID=opaque-random-value; Path=/; Secure; HttpOnly; SameSite=Lax

The browser stores the cookie according to its attributes and browser rules. On later requests that match the cookie's scope and sending conditions, the browser may send:

Cookie: JSESSIONID=opaque-random-value

The request header does not normally repeat the cookie's Secure, HttpOnly or SameSite attributes. Those are browser-side cookie instructions established through Set-Cookie.

1. Cookie attribute reference

Attribute Purpose Security consideration
Secure Sends the cookie only over secure transport under browser rules Use for session cookies in HTTPS deployments
HttpOnly Prevents access through browser script APIs such as document.cookie Reduces direct session-cookie theft through some XSS attacks
SameSite Restricts cookie sending in certain cross-site contexts Helps mitigate CSRF but is not a universal replacement for CSRF defenses
Path Limits the request paths for which the browser sends the cookie Narrow scope can reduce unintended exposure
Domain Controls which hosts receive the cookie Omitting it generally keeps the cookie host-only
Max-Age Specifies a relative persistence lifetime in seconds Controls browser persistence, not server-side session validity
Expires Specifies a cookie expiration date Browser retention is separate from server-side session expiration

These behaviors are defined by cookie standards and browser implementations; the OWASP Session Management Cheat Sheet provides practical security guidance.

2. Secure

The Secure attribute tells the browser to send the cookie only over secure HTTPS connections.

Without it, a session identifier could be exposed if the browser sends it over an unencrypted HTTP request under the applicable cookie rules.

For production authentication cookies, use HTTPS throughout the authenticated interaction and configure the cookie as secure.

Do not rely only on redirecting HTTP traffic to HTTPS. The session cookie itself must be configured correctly.

3. HttpOnly

HttpOnly prevents ordinary client-side JavaScript from reading the cookie through interfaces such as document.cookie.

This reduces the ability of injected JavaScript to directly extract the session identifier.

However, HttpOnly does not make XSS harmless. Malicious script running in the application's origin may still be able to issue requests as the user, even if it cannot read the cookie.

Therefore:

  • Use HttpOnly for session cookies.
  • Still prevent XSS through appropriate application controls.
  • Do not treat HttpOnly as a replacement for safe rendering or server-side authorization.

4. SameSite

The common values are:

  • Strict: The browser restricts sending the cookie with cross-site requests more aggressively.
  • Lax: Allows some cross-site top-level navigations, while restricting many cross-site subrequests.
  • None: Allows cross-site sending when other browser rules permit it; modern browsers require Secure with SameSite=None.

The choice affects both security and user experience.

For example, Strict may be appropriate for a sensitive banking interface that does not need to preserve login state when the user arrives from an external link. Lax can offer a more convenient balance for many web applications.

The correct choice depends on the application's navigation patterns and threat model.

Important Distinction

A site can be cross-origin but still same-site. SameSite is not equivalent to the same-origin policy, and it does not isolate different applications merely because they use different subdomains.

OWASP recommends treating SameSite as defense in depth and explains the conditions under which additional CSRF protection is needed. (OWASP Reference)

5. Path and Domain

Suppose the application sets:

Set-Cookie: JSESSIONID=opaque-value; Path=/

The cookie is eligible to be sent for matching paths under the host that set it.

A Domain attribute can expand cookie scope to subdomains. For example, setting Domain=example.com can make the cookie available to matching hosts under that domain.

That may be necessary for some architectures, but it increases the number of systems that could influence or receive the cookie.

For sensitive session cookies, prefer omitting Domain unless sharing across subdomains is an explicit requirement.

The Path attribute is a scoping mechanism, not a complete security boundary between applications on the same host.

6. Max-Age, Expires and server-side expiration

There are two distinct lifetimes:

  1. Cookie persistence: How long the browser retains or sends the cookie.
  2. Session validity: How long the server accepts the corresponding session.

These must not be confused.

A browser can retain a cookie after the server has invalidated its session. The browser may continue sending the identifier, but the server should reject it because the associated session no longer exists or is no longer valid.

Conversely, clearing a cookie in the browser does not invalidate a stolen copy held by an attacker. Server-side invalidation is essential.

A session cookie without Max-Age or Expires is generally treated as a non-persistent browser cookie, but browser session restoration can complicate assumptions about browser closure.

Do not use browser closure as the security mechanism for ending an authenticated session.

7. Cookie prefixes

Modern browsers support cookie prefixes that enforce additional restrictions.

For example, a __Host- cookie must be set with Secure, must have Path=/, and must not specify a Domain attribute.

A session cookie using this prefix can help protect against certain subdomain cookie-setting attacks, provided the browser enforces the prefix requirements.

Example:

Set-Cookie: __Host-SessionID=opaque-value; Path=/; Secure; HttpOnly; SameSite=Lax

Whether a framework can be configured to use this exact name depends on the application and container setup. Do not assume that changing the cookie name alone implements the necessary protections. (OWASP Reference)

E. Session fixation versus session hijacking

These are two different attacks. Understanding the distinction is essential because their primary defenses differ.

1. Session fixation

In a session-fixation attack, the attacker attempts to make the victim authenticate using a session identifier already known to the attacker.

A simplified attack sequence:

Session Fixation Attack Flow
sequenceDiagram participant A as Attacker participant V as Victim Browser participant S as Application A->>S: Obtain or influence a pre-login session ID S-->>A: Pre-login session ID A->>V: Attempt to make victim use that session ID V->>S: Authenticate using the affected session Note over S: Vulnerable design retains the same session ID A->>S: Reuse the known session ID S-->>A: Potential access to victim's authenticated session

The attack succeeds only if the attacker can get the victim to use the known identifier and the application fails to replace or otherwise protect the identifier when authentication changes the session's privilege level.

The primary defense is to rotate the session identifier when the user authenticates, so the identifier known before login cannot be used to access the authenticated session.

Spring Security provides session-fixation protection and supports strategies such as changing the session ID or creating a new session. The framework's behavior depends on its configured strategy and servlet-container capabilities. (Spring Docs)

2. Session hijacking

In session hijacking, the attacker obtains an already valid session identifier and attempts to use it to impersonate the session owner.

Potential sources include:

  • Session identifiers exposed over unencrypted traffic.
  • Malware or a compromised client.
  • Leakage through application logs or debugging tools.
  • An XSS vulnerability that enables attacker-controlled requests.
  • Improperly scoped cookies or other application vulnerabilities.

A simplified flow:

Session Hijacking Flow
sequenceDiagram participant U as Legitimate User participant S as Server participant A as Attacker U->>S: Request with valid session cookie S-->>U: Authorized response Note over A,U: Attacker obtains the session ID A->>S: Request using stolen session ID S->>S: Resolve session and apply security checks S-->>A: Potentially authorized response

If the server accepts the stolen identifier as a valid authenticated session and no additional control detects the misuse, the attacker may be able to act as the user.

The primary defenses include:

  • Secure, unpredictable session identifiers.
  • HTTPS throughout the authenticated interaction.
  • Secure and HttpOnly cookie attributes.
  • Short, appropriate server-side session lifetimes.
  • Session invalidation and renewal at security-sensitive transitions.
  • Detection of suspicious session behavior.
  • Preventing XSS and other vulnerabilities that facilitate session theft.

3. Comparison

Dimension Session fixation Session hijacking
Attacker's goal Make the victim authenticate with an attacker-known identifier Obtain and reuse a valid session identifier
Typical timing Before or during authentication After a usable session exists
Key weakness Session identity is not safely replaced at a privilege transition A valid session credential is exposed or stolen
Primary defense Session-ID rotation at authentication Protect the identifier, detect misuse and invalidate compromised sessions

A secure session implementation must defend against both.

4. Why TLS alone is insufficient

TLS helps prevent network interception of the session identifier, but it does not protect against every way a session can be compromised.

For example, a session identifier could be exposed through logs, browser compromise or an application vulnerability even when all traffic uses HTTPS.

Similarly, HttpOnly reduces direct cookie access by JavaScript, but does not prevent malicious same-origin script from issuing requests.

Session security therefore requires multiple complementary controls.

F. Session expiration, logout and invalidation

A session should have a defined lifecycle rather than remain valid indefinitely.

1. Three important expiration concepts

Idle timeout: The session expires after a period without qualifying activity.

Absolute timeout: The session expires after a maximum total lifetime, regardless of continued activity.

Cookie expiration: The browser stops retaining or sending the cookie according to its persistence rules.

Idle and absolute timeouts are server-side security policies. Cookie expiration is a client-side behavior and cannot replace them.

For a financial application, a session might have an idle timeout of 15 minutes and an absolute timeout of several hours. These are illustrative values, not universal recommendations. The appropriate values depend on the sensitivity of the application, expected usage and risk assessment.

An idle timeout is useful against abandoned authenticated sessions. An absolute timeout limits how long a continuously used or compromised session can remain valid without reauthentication.

2. Session lifecycle state machine

Session State Transitions
stateDiagram-v2 [*] --> Anonymous Anonymous --> Authenticated: Successful login Authenticated --> Authenticated: Valid request Authenticated --> Expired: Idle or absolute timeout Authenticated --> Invalidated: Logout or administrative revocation Authenticated --> Reauthenticated: Security-sensitive event Reauthenticated --> Authenticated: Verification succeeds Expired --> Anonymous: New login required Invalidated --> Anonymous: New login required

This is a conceptual state model. An actual application may have more states, such as temporarily restricted accounts or sessions requiring additional verification.

3. What logout must do

A secure logout should invalidate the session on the server and clear the browser's session cookie.

For a Servlet-based application:

import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import jakarta.servlet.http.HttpSession;

public class LogoutService {

    public void logout(
            HttpServletRequest request,
            HttpServletResponse response) {

        HttpSession session = request.getSession(false);

        if (session != null) {
            session.invalidate();
        }

        var cookie = new jakarta.servlet.http.Cookie(
                "JSESSIONID", "");

        cookie.setPath("/");
        cookie.setMaxAge(0);
        cookie.setHttpOnly(true);
        cookie.setSecure(true);

        response.addCookie(cookie);
    }
}

This illustrates the two operations, but it is not a complete production logout implementation.

The cookie-clearing attributes must match the actual cookie's name, path and domain scope. If the application uses a custom cookie name or prefix, the example must be adapted. A production implementation should also account for the application's framework configuration and CSRF requirements.

Most importantly, session.invalidate() removes the server-side session from the relevant session implementation. Clearing the cookie tells the browser to stop retaining the corresponding identifier. Both actions serve different purposes.

4. Logout failure scenarios

Consider the following cases:

  • Only the cookie is cleared: A stolen copy of the identifier might still work if the server session remains valid.
  • Only the server session is invalidated: The browser may continue sending the stale cookie, but the server should reject it.
  • The session store is distributed: The invalidation must take effect in the shared session-management system, not just in one application instance.
  • The session was already expired: Logout should still complete safely without assuming that an active session exists.

The security property to test is that the old session identifier cannot be used to access the protected resource after logout.

G. Session-ID rotation and security-sensitive transitions

Session identifiers should not remain unchanged across every security transition.

1. Why rotate after login?

Before authentication, an application may maintain anonymous state, such as a shopping cart or navigation preferences.

After successful authentication, the session becomes associated with an authenticated identity. This is a change in privilege level.

If the identifier remains attacker-known, the application may be vulnerable to session fixation.

The correct behavior is to rotate the session identifier or use an appropriate session-fixation protection strategy.

2. Spring Security strategies

Spring Security supports session-fixation strategies including:

  • changeSessionId: Change the identifier while retaining the session and its attributes, using servlet-container support.
  • newSession: Create a clean session, retaining the relevant Spring Security-related attributes but not generally copying arbitrary existing session attributes.
  • migrateSession: Create a new session and migrate the previous session attributes.

The default strategy depends on the servlet-container capabilities and Spring Security configuration. For modern Servlet 3.1+ containers, changeSessionId is the standard default behavior in Spring Security's session-fixation protection configuration. (Spring Docs)

The correct strategy depends on what the application stores in the pre-authentication session and whether that data should survive login.

3. When else might rotation or reauthentication be needed?

Consider security-sensitive events such as:

  • A user changes their password.
  • A user completes account recovery.
  • An administrator elevates privileges.
  • The application detects a compromised session.
  • The user changes important account-security settings.

Depending on the application, these events may require session renewal, invalidation of other sessions or reauthentication.

Do not blindly invalidate all sessions for every low-risk profile change. Define the security policy based on the consequences of compromise and the application's usability requirements.

H. Concurrent sessions and session limits

A user may sign in from multiple browsers, devices or application instances. Session management must define whether those sessions are allowed to coexist.

1. Common policies

Policy Behavior Trade-off
Unlimited concurrent sessions Each login can create another session Convenient, but more active credentials may remain exposed
One active session per user A new login may invalidate an older session Limits simultaneous use, but can disrupt legitimate users
Maximum N sessions Allows a bounded number of active sessions Balances convenience and exposure
Device/session management Lets users inspect and revoke sessions More complex but provides useful control

A financial application might allow a customer to use a laptop and mobile device simultaneously while limiting unusually large numbers of concurrent sessions.

2. The implementation challenge

Suppose the application runs on three instances:

                Load Balancer
                /     |     \
           App A    App B    App C
                \     |     /
                 Shared Session Store

If session limits are maintained only in each application's local memory, App A may believe a user has one session while App B independently creates another.

To enforce a global session limit, the design needs shared session-management state or another mechanism that coordinates concurrent logins.

3. Race conditions

Imagine the policy permits only one active session.

Two login requests arrive simultaneously:

  1. Request A checks that no session exists.
  2. Request B checks the same state.
  3. Both create sessions.
  4. Both believe they have complied with the policy.

A correct design needs atomic coordination or a suitable concurrency strategy. Depending on the implementation, this may involve transactional storage, a distributed coordination mechanism or framework-supported concurrent-session control.

A local synchronized block is not sufficient to coordinate multiple independent application processes.

4. Spring Security support

Spring Security supports concurrent-session control through its session-management features. The exact configuration requires appropriate session lifecycle integration, including event handling in some setups. (Spring Docs)

For this topic, the essential principle is that session limits are application-wide policies, not merely per-process counters.

Detailed framework architecture and configuration belong to Topic 4.

I. Session storage: in-memory versus Redis

The session store determines where authoritative session state lives and how the application retrieves, updates and invalidates it.

1. In-memory sessions

A simple deployment may use the servlet container's in-memory session storage.

Advantages:

  • Low-latency access.
  • Minimal additional infrastructure.
  • Straightforward development and debugging.

Disadvantages:

  • Session state may be lost on restart.
  • Other application instances may not share the state.
  • Large session populations consume application memory.
  • Deployments and failovers can disrupt active sessions.

This can be appropriate for development or a small single-instance application with acceptable session-loss behavior.

2. Distributed sessions with Redis

A distributed session design stores session state in a shared store, such as Redis, so that multiple application instances can access the same logical session.

Browser

Carries session identifier

Application A · Application B

Request processing

Shared session store

Lookup, update, expiry and invalidation

Advantages:

  • Session state can be shared across instances.
  • Application restarts need not destroy all sessions if the store retains the data.
  • Session management can scale independently of individual application processes.

Trade-offs:

  • Additional network latency.
  • Dependency failures can affect authenticated requests.
  • Serialization and session-schema changes require care.
  • The store becomes security-sensitive infrastructure.
  • Availability, eviction policies and capacity planning affect session behavior.

3. Session-store security

A shared store contains authentication-related state and must be protected accordingly.

Consider:

  • Restricting network access.
  • Using appropriate authentication and transport protection.
  • Limiting service privileges.
  • Avoiding sensitive values in session attributes.
  • Defining expiration and eviction behavior.
  • Protecting backups and administrative access.
  • Monitoring unexpected session creation, deletion or lookup failures.

Do not assume that Redis is safe merely because it is on a private network.

4. What happens if Redis is unavailable?

The correct behavior depends on the operation and security requirements.

For a protected request, if the application cannot determine whether the presented session is valid, it must not silently treat the request as authenticated.

A fail-closed policy may reject the request temporarily. This can reduce availability, so the application should also have timeouts, sensible dependency-failure handling and operational monitoring.

Do not automatically fall back to trusting a session identifier or a stale unauthenticated cache when the authoritative store is unavailable.

5. Session expiration and consistency

A distributed session store must ensure that expiration and invalidation behave consistently enough for the application's security requirements.

For example, if an administrator revokes a session, the system should define how quickly every application instance must stop accepting it.

The design should account for:

  • Store-level expiration.
  • Application-level session timeouts.
  • Cache invalidation.
  • Concurrent updates.
  • Temporary store failures.
  • Deployment and schema changes.

Sticky sessions at the load balancer may reduce some cross-instance traffic, but they do not eliminate the need to consider failover, invalidation and application restarts.

J. CSRF protection for cookie-based authentication

Cookie-based authentication creates an important browser-security consideration.

Browsers automatically attach applicable cookies to requests. This is useful because the user does not need to manually attach the session identifier to every request. However, it also means a malicious site may be able to trigger certain requests using the victim's existing authenticated browser context.

This is the basis of cross-site request forgery (CSRF).

1. Example attack

Suppose a customer is signed in to a financial application and the application has an endpoint that changes an account setting.

A malicious website attempts to cause the customer's browser to submit a request to that endpoint. If the browser sends the authentication cookie and the server accepts the request without adequate CSRF defenses, an unintended operation may succeed.

The attacker may not need to read the application's response. Causing the authenticated browser to submit the action can be enough.

2. Why a session cookie does not prove user intent

The session cookie establishes the browser's authenticated context, assuming the server validates it.

It does not, by itself, prove that the user intentionally initiated the current request.

These are separate questions:

  • Is the request associated with an authenticated session?
  • Was the state-changing request initiated through an acceptable interaction or protected request flow?

A secure design must address both.

3. Main CSRF defenses

For session-based applications, common defenses include:

  • CSRF tokens that the application verifies on state-changing requests.
  • Appropriate SameSite cookie attributes.
  • Origin or Referer validation where suitable.
  • Ensuring that safe HTTP methods such as GET do not change application state.
  • Appropriate request design and content-type handling.

OWASP recommends using CSRF tokens for state-changing operations in applications that rely on automatically attached browser credentials, with additional defenses selected according to the deployment. (OWASP Reference)

4. CSRF tokens: conceptual flow

A CSRF token is an additional value used to verify that a request came through an acceptable application flow.

Conceptually:

CSRF Token Verification Flow
sequenceDiagram participant B as Browser participant A as Application B->>A: Request form or protected page A-->>B: Page and CSRF token B->>A: State-changing request with cookie and token A->>A: Validate session and CSRF token alt Valid request A-->>B: Process operation else Invalid or missing token A-->>B: Reject request end

This is a conceptual diagram, not a complete CSRF implementation. Token generation, storage and comparison depend on the application's framework and deployment model.

5. What SameSite does and does not do

SameSite restricts cookie sending in certain cross-site contexts. It can substantially reduce CSRF risk.

But it is not a universal substitute for a CSRF token:

  • Some cross-site top-level navigations may still send cookies under Lax.
  • Same-site subdomains may not be isolated as an application developer expects.
  • Browser behavior and deployment details matter.
  • State-changing operations exposed through GET create additional risk.

For a sensitive application, combine an appropriate cookie policy with a deliberate CSRF defense and tests for state-changing endpoints.

6. When does CSRF matter?

It is especially relevant when the browser automatically attaches authentication credentials, as with ordinary session cookies.

A system using a different credential-transport design may have a different CSRF threat model, but it still needs to evaluate how credentials are supplied and how requests are authorized.

The important rule for this topic is that session-based authentication and CSRF protection must be designed together.

│   └── SessionAuthenticationInterceptor.java
└── service
    └── AccountService.java

The user repository and password encoder are reused from Topic 2.

2. Configure the session cookie and timeout

In application.properties:

server.servlet.session.timeout=15m
server.servlet.session.cookie.http-only=true
server.servlet.session.cookie.secure=true
server.servlet.session.cookie.same-site=lax

These settings illustrate a production-oriented HTTPS configuration.

  • The session timeout controls the container-managed inactivity timeout.
  • HttpOnly restricts JavaScript access to the session cookie.
  • Secure restricts cookie transmission to secure connections.
  • SameSite=Lax provides a useful baseline for many browser applications.

Use an HTTPS deployment when Secure is enabled. Local development over plain HTTP may require a separate development-only configuration; do not disable the production setting merely to make local testing convenient.

Also note that a container's session timeout does not necessarily enforce an independent absolute session lifetime. An absolute timeout requires an additional policy and implementation.

3. Define the login request

package com.example.sessiondemo.dto;

import jakarta.validation.constraints.Email;
import jakarta.validation.constraints.NotBlank;

public record LoginRequest(
        @NotBlank @Email String email,
        @NotBlank String password
) {}

The password is accepted only as request data for verification. It must not be stored in the session.

4. Establish session state after password verification

The service should use the existing account repository and PasswordEncoder from Topic 2.

package com.example.sessiondemo.service;

import com.example.account.entity.User;
import com.example.account.repository.UserRepository;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.stereotype.Service;

@Service
public class AccountService {

    private final UserRepository users;
    private final PasswordEncoder passwordEncoder;

    public AccountService(
            UserRepository users,
            PasswordEncoder passwordEncoder) {
        this.users = users;
        this.passwordEncoder = passwordEncoder;
    }

    public Long verifyCredentials(String email, String password) {
        User user = users.findByEmail(email)
                .orElseThrow(InvalidCredentialsException::new);

        if (!passwordEncoder.matches(
                password, user.getPasswordHash())) {
            throw new InvalidCredentialsException();
        }

        return user.getId();
    }
}

The InvalidCredentialsException is the same type of application-defined exception introduced in Topic 2.

This service returns the stable user ID only after successful password verification. It does not create a session or decide which resources the user may access.

5. Rotate the session identifier at login

For a Servlet-based demonstration, HttpServletRequest.changeSessionId() can rotate the identifier of an existing session. On a modern Servlet container, this is preferable to retaining an attacker-known pre-authentication identifier.

package com.example.sessiondemo.controller;

import com.example.sessiondemo.dto.LoginRequest;
import com.example.sessiondemo.service.AccountService;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpSession;
import jakarta.validation.Valid;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;

@RestController
@RequestMapping("/api")
public class AccountController {

    private final AccountService accountService;

    public AccountController(AccountService accountService) {
        this.accountService = accountService;
    }

    @PostMapping("/login")
    public ResponseEntity<Void> login(
            @Valid @RequestBody LoginRequest request,
            HttpServletRequest httpRequest) {

        Long userId = accountService.verifyCredentials(
                request.email(), request.password());

        HttpSession session = httpRequest.getSession(true);

        // Rotate the identifier before storing authenticated state.
        httpRequest.changeSessionId();

        session.setAttribute("authenticatedUserId", userId);

        return ResponseEntity.noContent().build();
    }

    @PostMapping("/logout")
    public ResponseEntity<Void> logout(
            HttpServletRequest httpRequest) {

        HttpSession session = httpRequest.getSession(false);

        if (session != null) {
            session.invalidate();
        }

        return ResponseEntity.noContent().build();
    }
}

This illustrates the essential lifecycle, but it omits some important production details:

  • Session creation and rotation should be coordinated with the authentication mechanism.
  • Cookie clearing and cookie scope must be handled consistently.
  • Login and logout endpoints must have an appropriate CSRF policy.
  • Authentication failures must return generic public errors.
  • Session expiry, concurrent logins and session-store behavior need explicit policies.

Spring Security provides session-fixation protection as part of its supported authentication flow, so production code should prefer the framework's mechanism rather than relying on custom controller code.

6. Restrict a protected endpoint

An interceptor can demonstrate how a request retrieves authenticated state from an existing session.

package com.example.sessiondemo.security;

import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import jakarta.servlet.http.HttpSession;
import org.springframework.stereotype.Component;
import org.springframework.web.servlet.HandlerInterceptor;

@Component
public class SessionAuthenticationInterceptor
        implements HandlerInterceptor {

    @Override
    public boolean preHandle(
            HttpServletRequest request,
            HttpServletResponse response,
            Object handler) throws Exception {

        HttpSession session = request.getSession(false);

        Object userId = session == null
                ? null
                : session.getAttribute("authenticatedUserId");

        if (!(userId instanceof Long)) {
            response.setStatus(
                    HttpServletResponse.SC_UNAUTHORIZED);
            return false;
        }

        return true;
    }
}

Register the interceptor for the protected route:

package com.example.sessiondemo.config;

import com.example.sessiondemo.security
        .SessionAuthenticationInterceptor;
import org.springframework.context.annotation.Configuration;
import org.springframework.web.servlet.config.annotation
        .InterceptorRegistry;
import org.springframework.web.servlet.config.annotation
        .WebMvcConfigurer;

@Configuration
public class SessionConfig implements WebMvcConfigurer {

    private final SessionAuthenticationInterceptor interceptor;

    public SessionConfig(
            SessionAuthenticationInterceptor interceptor) {
        this.interceptor = interceptor;
    }

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(interceptor)
                .addPathPatterns("/api/protected/**")
                .excludePathPatterns("/api/login", "/api/logout");
    }
}

For demonstration, create a protected endpoint:

package com.example.sessiondemo.controller;

import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpSession;
import org.springframework.web.bind.annotation.*;

import java.util.Map;

@RestController
@RequestMapping("/api/protected")
public class PortfolioController {

    @GetMapping("/portfolio")
    public Map<String, Object> portfolio(
            HttpServletRequest request) {

        HttpSession session = request.getSession(false);

        Long userId = (Long) session.getAttribute(
                "authenticatedUserId");

        return Map.of(
                "userId", userId,
                "message", "Authenticated session found"
        );
    }
}

This endpoint demonstrates the session lookup. It does not implement resource-level authorization or return real portfolio data. Those checks must be performed separately, and detailed authorization design belongs to Topic 5.

Production warning

A custom MVC interceptor is not a complete substitute for Spring Security. It can be bypassed by incorrect route configuration, may not cover every relevant request path and does not provide the framework's complete authentication, CSRF or security-context behavior. Do not deploy this educational implementation as a production authentication solution without replacing it with a properly configured security framework.

7. What happens on each request?

For the protected portfolio endpoint:

  1. The browser sends the session cookie.
  2. The servlet container resolves the session.
  3. The interceptor retrieves the existing session without creating a new one.
  4. The interceptor checks for the expected authenticated-state attribute.
  5. If the state is absent, the request is rejected.
  6. If the state exists, the controller executes.
  7. The application performs the appropriate business and resource-authorization checks.

This demonstrates the key session concept: the cookie carries the identifier; the server-side session carries the authentication-related state.

L. Request walkthroughs and failure scenarios

1. Successful login

Request:

POST /api/login
Content-Type: application/json

{
  "email": "alice@example.com",
  "password": "Example-Password-For-Testing"
}

Assuming valid credentials, the application verifies the password, creates or retrieves the session, rotates the session ID, and associates the authenticated user ID with the session.

The response should set or update the session cookie through the servlet container.

Subsequent requests carry that cookie, allowing the application to retrieve the corresponding server-side session.

2. Request without a session

GET /api/protected/portfolio

If there is no authenticated session, the interceptor returns 401 Unauthorized.

The request must not trigger a new authenticated session merely because the caller requests a protected resource.

3. Request with an expired session

The browser might still send an old cookie after the server-side session has expired.

The server should reject the request because the identifier no longer resolves to a valid authenticated session.

Depending on the framework and configuration, the response may be 401, a redirect to login, or another documented outcome.

4. Request after logout

After logout, the server invalidates the session.

Even if the client manually resends the old cookie, the application should not restore the old authenticated state. This is a critical negative test.

5. Session store unavailable

If the application uses a shared session store and that store becomes unavailable, the application may be unable to validate the session.

For protected operations, the application must not bypass the check and proceed as authenticated without reliable evidence. It should fail safely and expose an appropriate service error.

6. Session ID supplied through an unexpected mechanism

If an application accepts session identifiers from URL parameters or other unexpected locations, an attacker may be able to manipulate the identifier or expose it through logs, browser history or referrer information.

A session-based application should define and enforce an accepted session-ID transport mechanism, normally cookies, and test that alternative mechanisms are not inadvertently accepted. (OWASP Reference)

Session tests should establish that authenticated state persists when appropriate, changes when required, and cannot be reused after invalidation.

2. Example integration-test outline

A full Spring Boot integration test should use the actual session configuration and HTTP test client. The following is a test plan rather than a complete test class:

Test: loginCreatesAuthenticatedSession

1. Submit valid credentials to POST /api/login.
2. Capture the session cookie from the response.
3. Call GET /api/protected/portfolio with the cookie.
4. Assert the protected endpoint succeeds.
5. Assert the response corresponds to the authenticated test user.

A second test should prove invalidation:

Test: logoutInvalidatesExistingSession

1. Log in and capture the session cookie.
2. Call POST /api/logout with the required request protections.
3. Assert logout succeeds.
4. Replay the old session cookie.
5. Assert the protected endpoint rejects the request.

For production, these tests should exercise the actual Spring Security configuration rather than only a custom interceptor.

3. Testing session-ID rotation

The important assertion is not simply that a cookie exists after login. It is that the authenticated session is no longer accessible through the pre-authentication identifier.

Test the pre-login identifier against the protected endpoint after authentication. It must not grant access to the authenticated session.

4. Testing cookie attributes

Inspect actual Set-Cookie response headers in an integration or deployment test.

Verify that:

  • Secure is present in production.
  • HttpOnly is present.
  • SameSite matches the intended policy.
  • Domain is absent unless sharing is required.
  • Path is appropriate.
  • Cookie expiration aligns with the documented client-side policy.

Do not infer the production cookie configuration solely from a property file. Proxies, container settings and framework configuration may affect the final response.

2. Logging and observability

Useful session lifecycle events include:

  • Session creation.
  • Authentication and session-ID rotation.
  • Logout and invalidation.
  • Timeout expiration.
  • Rejected requests involving invalid session identifiers.
  • Administrative session revocation.
  • Session-store failures.

Logs should support investigation without exposing raw session identifiers. Where session-level correlation is needed, use a carefully designed non-reversible correlation value rather than logging the credential itself.

Protect the logs and any administrative interfaces that can inspect or revoke active sessions.

3. Recovery planning

A production application should define how to respond to:

  • A suspected stolen session.
  • A compromised browser or device.
  • A session-store outage.
  • Incorrect cookie attributes after deployment.
  • An accidental mass logout.
  • A vulnerability that requires invalidating active sessions.

For a suspected compromise, the system should be able to revoke affected sessions server-side. Merely asking users to clear their browser cookies is insufficient.

O. How a Senior Engineer Thinks About This

An experienced engineer does not select session settings by copying a configuration snippet. They identify the application's security requirements and understand how each setting affects the session lifecycle.

1. Design-review questions

Before approving a session-based application, ask:

  1. Session identity: Is the session ID sufficiently unpredictable, and does it reveal anything sensitive?
  2. Authentication transition: Is the session identifier rotated when authentication succeeds?
  3. Cookie policy: Are Secure, HttpOnly, SameSite, Path and Domain configured deliberately?
  4. Expiration: Is there an explicit server-side idle timeout and, where needed, an absolute timeout?
  5. Logout: Does logout invalidate server-side state, including in a distributed deployment?
  6. Concurrency: Can two simultaneous login requests violate a session limit?
  7. Scaling: Can every application instance validate and invalidate the same session correctly?
  8. CSRF: Can an attacker cause a victim's browser to initiate a state-changing request?
  9. Observability: Can engineers investigate session abuse without logging session credentials?
  10. Recovery: Can the application revoke sessions after a suspected compromise?

2. Common architectural mistakes

Mistake Why it is dangerous Better approach
Treating the cookie as the session itself Confuses client-side reference with server-side state Keep authoritative session state server-side
Keeping the same ID after login Can enable session fixation Use session-fixation protection
Clearing only the browser cookie on logout A stolen copy may remain usable Invalidate the server-side session
Relying on browser closure for expiry Browser restoration can preserve cookies Enforce server-side expiration
Storing sessions only in one process in a multi-instance system Other instances may not recognize the session Use a suitable shared session-management design
Treating SameSite as complete CSRF protection Some cross-site and same-site attack scenarios remain Apply a deliberate CSRF policy
Logging raw session IDs Logs become a source of credential theft Use safe session-event logging and non-reversible correlation

3. The most important architectural decision

The key trade-off is not simply whether sessions are old-fashioned or modern. It is whether the session architecture fits the application's requirements.

For a conventional web application, server-side sessions offer centralized control over authenticated state and straightforward server-side invalidation.

However, they introduce state-management responsibilities, especially when multiple instances must share sessions and honor revocation consistently.

The right choice depends on operational constraints, application architecture, security requirements and the expected user experience.

Q. Hands-on exercise — Session-Based Authentication

Practical assignment

Build a session-based portfolio API

Create a Java/Spring Boot application in which a customer logs in, accesses a protected endpoint and logs out by invalidating the server-side session.

Requirements

  • Reuse the password verification approach from Topic 2.
  • Establish server-side session state only after successful credential verification.
  • Rotate the session identifier at authentication.
  • Configure the session cookie deliberately.
  • Reject protected requests without a valid authenticated session.
  • Implement logout and server-side invalidation.
  • Define idle-timeout behavior and document whether an absolute timeout is required.
  • Explain how the design would change if the application used Redis and multiple instances.

Security requirements

  • Do not store plaintext passwords in the session.
  • Do not expose raw session IDs in logs.
  • Do not trust a session ID merely because it was supplied by the client.
  • Protect state-changing requests against CSRF.
  • Reject old session identifiers after logout or invalidation.
  • Do not allow store failures to bypass session validation.

Acceptance tests

  1. Correct credentials establish authenticated state.
  2. Incorrect credentials do not establish authenticated state.
  3. An unauthenticated request cannot access the protected endpoint.
  4. The session ID changes across the authentication transition.
  5. A valid session allows the protected request.
  6. Logout invalidates the session server-side.
  7. Reusing the old cookie after logout does not grant access.
  8. Expired sessions are rejected.
  9. Cookie attributes match the intended production configuration.
  10. State-changing requests follow the application's CSRF policy.

Optional extension

Add a shared Redis-backed session store and design a maximum-concurrent-sessions policy. Explain how the application handles concurrent logins, session revocation and a Redis outage.

Do not start by adding Redis or concurrent-session limits. First get the single-instance lifecycle correct, then introduce distributed-state concerns.
